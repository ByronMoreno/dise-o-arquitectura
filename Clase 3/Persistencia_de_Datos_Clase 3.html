1. Persistencia de Datos y Bases de Datos Empresariales

En desarrollo de software, la Persistencia de Datos es la propiedad de los datos de sobrevivir más allá de la vida útil del proceso que los creó. Sin persistencia, los datos que residen únicamente en la memoria RAM se perderían por completo cuando la aplicación se apaga o se reinicia.

Bases de Datos Relacionales (RDBMS)

Almacenan información en tablas formadas por columnas y filas. Garantizan integridad a través de restricciones y propiedades ACID (Atomicidad, Consistencia, Aislamiento y Durabilidad). Ejemplo: PostgreSQL, MySQL.

Bases de Datos NoSQL

Diseñadas para modelos de datos no relacionales, ideales para gran volumen de información no estructurada o de rápido crecimiento. Incluyen bases de datos documentales, clave-valor, y grafos. Ejemplo: MongoDB, Redis.

Introducción a Bases de Datos Empresariales

En entornos corporativos (enterprise), las bases de datos deben operar bajo requerimientos de alta concurrencia, escalabilidad horizontal/vertical y tolerancia a fallos. Las bases de datos empresariales utilizan estrategias avanzadas para garantizar la disponibilidad del negocio:

Connection Pooling (HikariCP)

Abrir y cerrar conexiones físicas a la BD es sumamente costoso. Un Pool mantiene una colección de conexiones abiertas y activas para reutilizarlas de inmediato en peticiones entrantes, optimizando la latencia del sistema.

Transacciones ACID Estrictas

Aseguran la consistencia de los datos financieros u operativos. Las operaciones ocurren por completo (Atomicidad), respetan reglas del negocio (Consistencia), no interfieren entre sí (Aislamiento) y persisten ante caídas (Durabilidad).

Alta Disponibilidad & Réplicas

Arquitecturas de replicación (Master-Slave o Multi-Master) permiten delegar operaciones pesadas de lectura a nodos esclavos secundarios, manteniendo el nodo maestro exclusivamente para escrituras.

3. Patrón Repository y Diseño de Acceso a Datos

El patrón de diseño Repository actúa como un mediador entre el dominio (lógica de negocio) y las capas de acceso a datos. Proporciona una interfaz orientada a colecciones de objetos para que el resto de la aplicación no tenga conocimiento de cómo se guardan o recuperan los datos físicamente.

Abstracción de Datos

Oculta la tecnología de almacenamiento subyacente (JDBC, JPA, NoSQL, archivos) de la lógica de negocio central de la aplicación.

Facilidad de Testing

Permite reemplazar fácilmente la base de datos real con mockups (simulaciones en memoria) para ejecutar pruebas unitarias rápidas.

Código Limpio y Reutilizable

Centraliza las consultas a la base de datos eliminando la duplicación de código SQL o consultas JPA en múltiples servicios de negocio.

Diseño de Acceso: DAO vs. Repository

En el diseño arquitectónico de acceso a datos, es común confundir el patrón tradicional DAO (Data Access Object) con el patrón moderno Repository. Ambos desacoplan la base de datos, pero operan bajo filosofías diferentes:

DAO (Data Access Object)

Centrado en: Tablas físicas y SQL
Cardinalidad: 1 DAO por Tabla (1:1)
Lógica: Mapea consultas SQL CRUD nativas
Nivel de Abstracción: Bajo (Próximo a la BD)
Diferencias

Repository

Centrado en: Dominio y Objetos de Negocio
Cardinalidad: 1 Repository por Agregado Raíz
Lógica: Simula una colección en memoria
Nivel de Abstracción: Alto (Próximo al Dominio) 
package com.unibe.arquitectura.repository;

import com.unibe.arquitectura.model.Usuario;
import java.util.List;
import java.util.Optional;

// Interfaz limpia expuesta al dominio de la aplicación
public interface UserRepository {
    Usuario save(Usuario usuario);
    Optional<Usuario> findById(Long id);
    List<Usuario> findAll();
    void deleteById(Long id);
    
    // Método de negocio específico
    Optional<Usuario> findByEmail(String email);
}
package com.unibe.arquitectura.repository.impl;

import com.unibe.arquitectura.model.Usuario;
import com.unibe.arquitectura.repository.UserRepository;
import java.sql.*;
import java.util.Optional;

// Implementación de bajo nivel (oculta los detalles de JDBC SQL)
public class UserRepositoryImpl implements UserRepository {
    private final Connection connection;

    public UserRepositoryImpl(Connection connection) {
        this.connection = connection;
    }

    @Override
    public Optional<Usuario> findByEmail(String email) {
        String sql = "SELECT * FROM usuarios WHERE email = ?";
        try (PreparedStatement stmt = connection.prepareStatement(sql)) {
            stmt.setString(1, email);
            try (ResultSet rs = stmt.executeQuery()) {
                if (rs.next()) {
                    Usuario user = new Usuario(rs.getLong("id"), rs.getString("nombre"), rs.getString("email"));
                    return Optional.of(user);
                }
            }
        } catch (SQLException e) {
            throw new RuntimeException("Error al buscar usuario por email", e);
        }
        return Optional.empty();
    }
    
    // ... Los demás métodos CRUD encapsulan sentencias SQL similares ...
}
package com.unibe.arquitectura.repository;

import com.unibe.arquitectura.model.Usuario;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.stereotype.Repository;
import java.util.Optional;

// Con Spring Data JPA, la implementación JDBC/JPA se genera dinámicamente.
@Repository
public interface UserRepository extends JpaRepository<Usuario, Long> {
    
    // Spring genera la consulta automáticamente basándose en el nombre del método
    Optional<Usuario> findByEmail(String email);
}

4. ORM (Object-Relational Mapping)

El mapeo objeto-relacional (ORM) es una técnica de programación para convertir datos entre sistemas de bases de datos relacionales y el paradigma de lenguajes orientados a objetos. Resuelve la incompatibilidad técnica conocida como el Desfase de Impedancia.

Paradigma Orientado a Objetos (Java)

Clase public class Usuario
Atributo / Propiedad private String email;
Objeto (Instancia) new Usuario(1L, "Ana")
Referencia directa / Colección List<Pedido> pedidos;
Mapeo (ORM)

Paradigma Relacional (SQL DB)

Tabla CREATE TABLE usuarios
Columna email VARCHAR(150)
Fila / Registro 1 | "Ana" | "ana@mail.com"
Clave Foránea (FK) usuario_id BIGINT

5. Introducción a JPA y Hibernate

Es fundamental diferenciar las dos tecnologías: JPA (Java Persistence API) es la especificación estándar (un conjunto de interfaces y directrices oficiales de Java SE/EE), mientras que Hibernate es la implementación concreta más popular de ese estándar ORM.

JPA (Especificación)

Define las anotaciones estándar (como @Entity, @Table, @Id) y la interfaz EntityManager. No hace trabajo real, solo establece el "contrato".

Hibernate (Proveedor/Motor)

Lee los metadatos de las anotaciones de JPA, abre las conexiones JDBC subyacentes y genera las sentencias SQL nativas para bases de datos relacionales.

Explorador de Anotaciones de JPA: Haz clic en las líneas del código de abajo para ver una descripción interactiva del mapeo de la Entidad. 

// Mapeo de Entidad Principal
@Entity@Table(name = "usuarios")public class Usuario {

    // Identificador único (Clave Primaria)
    @Id    @GeneratedValue(strategy = GenerationType.IDENTITY)    private Long id;

    // Atributo mapeado a columna obligatoria
    @Column(name = "email", unique = true, nullable = false)    private String email;

    // Asociación de Uno a Muchos
    @OneToMany(mappedBy = "usuario", cascade = CascadeType.ALL)    private List<Pedido> pedidos;
}

@Entity

Es la anotación fundamental de JPA a nivel de clase. Le indica al proveedor de persistencia (Hibernate) que esta clase Java es una entidad persistente cuyo ciclo de vida será gestionado por el Entity Manager y representará registros en la base de datos.

Práctica: Diseño de Capa de Persistencia

Aplica los conceptos estudiados diseñando la capa de persistencia para un Sistema de Gestión de Biblioteca. Debes modelar la relación entre estudiantes, libros y préstamos de libros (un estudiante puede realizar varios préstamos de diferentes libros).

Para representar la relación de muchos a muchos histórica entre Estudiante y Libro con atributos propios (fecha del préstamo y si está activo), se crea la tabla intermedia **prestamos** de la siguiente manera:

estudiantes
  • PK idBIGINT
  • nombreVARCHAR
1:N
prestamos
  • PK idBIGINT
  • FK estudiante_idBIGINT
  • FK libro_idBIGINT
  • fecha_prestamoDATE
  • activoBOOLEAN
N:1
libros
  • PK idBIGINT
  • tituloVARCHAR
  • isbnVARCHAR
@Entity
@Table(name = "prestamos")
public class Prestamo {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne
    @JoinColumn(name = "estudiante_id", nullable = false)
    private Estudiante estudiante;

    @ManyToOne
    @JoinColumn(name = "libro_id", nullable = false)
    private Libro libro;

    @Column(name = "fecha_prestamo")
    private LocalDate fechaPrestamo;

    private boolean activo;
}
@Repository
public interface PrestamoRepository extends JpaRepository<Prestamo, Long> {
    
    // Retorna todos los préstamos activos de un estudiante específico usando Derived Queries
    List<Prestamo> findByEstudianteIdAndActivoTrue(Long estudianteId);
    
    // Query personalizado con JPQL para buscar préstamos por el ISBN del libro
    @Query("SELECT p FROM Prestamo p WHERE p.libro.isbn = :isbn")
    List<Prestamo> findByIsbn(@Param("isbn") String isbn);
}

Guía de Estudio: Examen Parcial I

El examen parcial de la sesión de los miércoles evalúa los conceptos teóricos y prácticos fundamentales vistos hasta la fecha en la asignatura. A continuación, se presenta un resumen de los temas clave:

1. Fundamentos de Diseño

- Abstracción: Aislar elementos del problema enfocándose en lo relevante.
- Encapsulamiento: Agrupar datos y operaciones, ocultando el estado interno.
- Acoplamiento: Nivel de interdependencia entre módulos (se busca que sea Bajo para facilitar cambios).
- Cohesión: Medida de qué tan enfocada está una clase en una sola tarea (se busca que sea Alta).

2. Principios SOLID

- SRP: Una clase debe tener una sola razón para cambiar.
- OCP: Abierto a extensión, cerrado a modificación.
- LSP: Subclases deben poder sustituir a sus clases base sin alterar el comportamiento.
- ISP: Interfaces pequeñas y específicas.
- DIP: Depender de abstracciones, no de detalles.

3. Calidad de Software

De acuerdo a la norma de calidad internacional ISO/IEC 25010, las características clave de calidad del producto de software son:
- Adecuación Funcional, Eficiencia de Rendimiento, Compatibilidad, Usabilidad, Fiabilidad, Seguridad, Mantenibilidad (analizabilidad, modificabilidad, testeabilidad) y Portabilidad.

4. Relaciones UML

Representaciones visuales del Diagrama de Clases:
- Asociación: Conexión estructural simple (ej. Cliente compra Producto).
- Agregación (Rombo vacío): Relación todo-parte débil (ej. Universidad - Profesor).
- Composición (Rombo relleno): Relación todo-parte fuerte (ej. Libro - Páginas).
