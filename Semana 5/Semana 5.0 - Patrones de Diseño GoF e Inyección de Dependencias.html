Patrones de Diseño GoF e Inyección de Dependencias

Los patrones de diseño son soluciones probadas, documentadas y reutilizables a problemas recurrentes en el diseño de software orientado a objetos. En esta semana exploramos los 8 patrones cardinales de la "Gang of Four" (GoF), combinados con los principios de Inversión de Control (IoC) y contenedores modernos de Inyección de Dependencias como Spring Boot.

1 ¿Qué es un Patrón de Diseño GoF?

Estructura canónica: Nombre, Problema, Solución y Consecuencias

Propuestos originalmente en 1994 por Erich Gamma, Richard Helm, Ralph Johnson y John Vlissides (GoF). No son bibliotecas ni fragmentos de código listos para copiar y pegar: son plantillas conceptuales que describen cómo organizar clases e interfaces para resolver un dilema de diseño con flexibilidad y bajo acoplamiento.

2 Patrones Creacionales

Mecanismos abstractos de instanciación que desacoplan el qué del cómo

🏭 Factory Method

Define una interfaz para crear un objeto, pero delega a las subclases o métodos de fábrica la decisión de qué clase exacta instanciar.

Caso real: Crear procesadores de pago (StripeProcessor, PayPalProcessor) según la pasarela seleccionada.

🔒 Singleton

Garantiza que una clase posea una única instancia global en todo el ciclo de vida de la JVM y provee un punto de acceso único.

Alerta de diseño: Debe implementarse con cuidado (preferiblemente vía Beans de Spring o enum) para no obstaculizar las pruebas unitarias con estado global mutable.

🔨 Builder

Separa la construcción de un objeto complejo de su representación final, permitiendo crear objetos inmutables mediante una API fluida (Fluent Interface).

Caso real: Construcción de una Matricula con múltiples líneas, descuentos, seguros y recargos sin constructores telescópicos con 12 parámetros.

3 Patrones Estructurales

Composición de clases e interfaces para formar estructuras más complejas

🔌 Adapter

Convierte la interfaz de una clase existente en otra interfaz que el cliente espera, permitiendo que clases con interfaces incompatibles trabajen juntas.

Ejemplo: Adaptar un servicio SOAP/XML antiguo de una entidad bancaria a la interfaz REST/JSON moderna de la universidad.

🏛️ Facade (Fachada)

Provee una interfaz unificada y de alto nivel a un subsistema complejo (compuesto por múltiples repositorios, servicios y clientes HTTP), simplificando drásticamente su consumo.

Ejemplo: MatriculaFacade.completarInscripcion() que oculta la llamada secuencial a 4 servicios internos.

🎨 Decorator

Añade responsabilidades y comportamientos dinámicamente a un objeto sin alterar su clase original ni recurrir a la herencia explosiva.

Ejemplo: Decorar un servicio de cálculo con una capa de caché en Redis o una capa de logging y métricas Prometheus.

4 Patrones de Comportamiento

Distribución dinámica de algoritmos, responsabilidades y comunicación

♟️ Strategy

Define una familia de algoritmos intercambiables, encapsulando cada uno en una clase independiente bajo una misma interfaz. Permite cambiar el algoritmo en tiempo de ejecución sin modificar al cliente que lo utiliza.

Ejemplo Strategy: Algoritmos de Aranceles
public interface CalculoArancelStrategy {
    BigDecimal calcular(Estudiante est, int totalCreditos);
}

public class ArancelPregradoRegular implements CalculoArancelStrategy { ... }
public class ArancelPosgradoExtranjero implements CalculoArancelStrategy { ... }

📢 Observer

Define una relación de dependencia uno a muchos entre objetos, de manera que cuando el sujeto central cambia de estado, todos sus observadores suscritos son notificados y actualizados automáticamente.

Ejemplo Observer: Eventos de Dominio en Spring
// Sujeto emite evento
publisher.publishEvent(new MatriculaConfirmadaEvent(matriculaId));

// Observadores desacoplados
@EventListener
public void notificarEstudiante(MatriculaConfirmadaEvent e) { ... }

@EventListener
public void reservarCupoEnMoodle(MatriculaConfirmadaEvent e) { ... }

5 Inversión de Control (IoC) e Inyección de Dependencias

El principio de Hollywood: "No nos llames a nosotros, nosotros te llamaremos a ti"

Modalidad de Inyección Sintaxis Típica (Spring / Java) Veredicto y Buenas Prácticas
Inyección por Constructor (Recomendada) public MiServicio(Repositorio repo) { this.repo = repo; } ✅ Mejor práctica empresarial: Garantiza inmutabilidad (campos final), detecta dependencias circulares en compilación y permite tests unitarios sin levantar el framework.
Inyección por Setter public void setRepositorio(Repositorio repo) { ... } ⚠️ Uso condicional: Para dependencias opcionales que pueden cambiar durante el ciclo de vida del objeto.
Inyección por Campo (Field Injection) @Autowired private Repositorio repo; ❌ Desaconsejada / Bad Practice: Oculta dependencias, viola la inmutabilidad y hace imposible instanciar la clase en tests unitarios puros sin reflexión.

6 Cuestionario de Patrones GoF e IoC

Valida tu criterio técnico para seleccionar y justificar patrones

1. ¿Qué patrón de diseño GoF es el indicado para construir un objeto complejo paso a paso, asegurando que el objeto resultante sea inmutable y evitando constructores con decenas de parámetros?
2. Necesitas integrar una librería bancaria externa cuya interfaz no coincide con los métodos que tu arquitectura espera. ¿Qué patrón estructural resuelve este problema sin modificar el código de la librería externa?
3. ¿Por qué la inyección de dependencias por constructor se considera superior a la inyección por campo (@Autowired directo en variable privada)?
