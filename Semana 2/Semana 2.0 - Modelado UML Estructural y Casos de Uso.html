UNIDAD 1 RDA2: MODELADO ORIENTADO A OBJETOS

Modelado Estructural y de Comportamiento con UML

UML (Unified Modeling Language) es el estándar formal de la industria para visualizar, especificar, construir y documentar los artefactos de un sistema de software. Esta semana dominamos los dos diagramas estructurales y de límites cardinales: Diagramas de Casos de Uso con especificación textual formal y Diagramas de Clases con semántica estricta de relaciones.

1 El Lenguaje de Modelado Unificado (UML 2.5)

Taxonomía de diagramas estructurales vs de comportamiento

Estructurales (Estáticos)

Representan la organización física o lógica de los elementos del software sin considerar el tiempo:
• Diagrama de Clases: Entidades, métodos, atributos y vínculos.
• Diagrama de Componentes: Módulos y artefactos empaquetados.
• Diagrama de Despliegue: Nodos físicos, contenedores y hardware.

De Comportamiento (Dinámicos)

Capturan la ejecución temporal, intercambio de mensajes y transiciones de estado:
• Diagrama de Casos de Uso: Frontera del sistema y metas de los actores.
• Diagrama de Secuencia: Mensajes cronológicos entre instancias.
• Diagrama de Estados y Actividades: Ciclos de vida y flujos de trabajo.

2 Diagramas de Casos de Uso y sus Relaciones

Frontera del sistema, Actores primarios/secundarios y dependencias

Elemento / Relación Notación Gráfica Semántica y Regla de Uso
Actor Figura de palo (Stickman) o clase <<actor>> Rol que interactúa con el sistema (Usuario humano, cron job o API externa).
Límite del Sistema Rectángulo rotulado con el nombre del software Encapsula los casos de uso dentro del alcance del desarrollo; los actores quedan fuera.
Inclusión (<<include>>) Línea discontinua con flecha abierta hacia el caso incluido Obligatorio: El caso base SIEMPRE invoca al caso incluido para completarse (ej. Matricular Materia → <<include>> → Validar Prerrequisitos).
Extensión (<<extend>>) Línea discontinua con flecha desde el caso extensor al caso base Opcional / Condicional: El caso base puede ejecutarse sin la extensión; esta solo se dispara si se cumple una condición o punto de extensión (ej. Pagar con Descuento Especial → <<extend>> → Pagar Matrícula).
Generalización Flecha continua con punta de triángulo hueco Herencia entre actores (ej. Docente y Estudiante heredan de Usuario) o entre casos de uso especializados.

3 Especificación Textual Formal de Casos de Uso

El diagrama muestra el mapa; la especificación textual contiene la ingeniería

Un diagrama de casos de uso sin especificación textual carece de valor prescriptivo. Toda organización profesional utiliza plantillas estandarizadas:

Plantilla Estándar: Caso de Uso CU-03 (Registro de Asignaturas) 
ID: CU-03
Nombre: Matricular Asignaturas del Período Académico
Actor Principal: Estudiante
Actores Secundarios: Sistema de Gestión Financiera (ERP), Servicio de Correo
Precondiciones:
  1. El estudiante ha autenticado sus credenciales en el portal institucional.
  2. El período ordinario de matrícula se encuentra en estado ABIERTO.
Flujo Principal (Camino Básico):
  1. El estudiante ingresa a la sección "Matrícula Ordinaria".
  2. El sistema consulta y despliega la oferta académica habilitada según la malla curricular.
  3. El estudiante selecciona las asignaturas y los paralelos de su preferencia.
  4. El sistema ejecuta el caso <<include>> CU-04 "Validar Prerrequisitos y Co-requisitos".
  5. El sistema calcula los créditos y el valor arancelario total a cancelar.
  6. El estudiante confirma la selección de materias.
  7. El sistema reserva los cupos en los paralelos y emite la orden de liquidación en estado PENDIENTE.
  8. El caso de uso finaliza exitosamente.
Flujos Alternativos / Excepciones:
  4a. Cruce de Horario Detectado:
      - El sistema alerta el solapamiento entre dos asignaturas seleccionadas.
      - El estudiante debe desmarcar una de las dos asignaturas para reanudar el flujo en el paso 3.
  4b. Prerrequisito No Aprobado:
      - El sistema bloquea la materia y notifica el código del prerrequisito adeudado.
Postcondiciones:
  - Los cupos del estudiante se descuentan del aforo máximo disponible.
  - Se genera un registro de auditoría con la fecha, hora e IP de la transacción.

4 Diagramas de Clases: Estructura y Visibilidad

Entidades de dominio, operaciones y contratos orientados a objetos

Anatomía de una Clase UML

Consta de 3 compartimentos obligatorios:
1. Nombre de la clase: En negrita centrado. Si es abstracta, va en cursiva o con <<abstract>>.
2. Atributos: visibilidad nombre : tipo = valorPorDefecto
3. Operaciones / Métodos: visibilidad nombre(param: tipo) : tipoRetorno

Modificadores de Acceso UML:
• + Público (Public)
• - Privado (Private)
• # Protegido (Protected)
• ~ Paquete (Package / Default)

Modelo de Dominio vs Diagrama de Diseño

• Modelo de Dominio (Conceptual): Representa conceptos del mundo real del negocio. No incluye tipos de datos de programación, métodos auxiliares ni tecnologías como ORM o controladores HTTP.

• Diagrama de Clases de Diseño (Implementación): Contiene la especificación exacta de clases de software con tipos estrictos (UUID, BigDecimal), getters, setters, interfaces y patrones de diseño aplicados.

5 Relaciones entre Clases: Agregación vs Composición

Diferenciación crucial para la integridad del ciclo de vida de los objetos

⚪ Agregación (Vínculo Débil / "Tiene Un")

Se representa con un rombo hueco/blanco en el lado del contenedor.

Ciclo de vida independiente: La parte puede existir sin el todo. Si se destruye el contenedor, los elementos contenidos sobreviven.

Ejemplo: Una Universidad y sus Profesores. Si la universidad cierra, los profesores siguen existiendo y pueden trabajar en otra institución.

⚫ Composición (Vínculo Fuerte / "Compuesto De")

Se representa con un rombo lleno/negro en el lado del contenedor.

Ciclo de vida dependiente: La parte no tiene sentido de existencia fuera del todo. La destrucción del contenedor elimina en cascada todas sus partes.

Ejemplo: Una Factura y sus LineasDetalle, o una Matrícula y sus RegistrosDeMateria.

6 Código PlantUML Listo para Renderizar

Automatización de diagramas como código (Diagrams as Code)

PlantUML: Diagrama de Clases del Sistema Académico 
@startuml
skinparam classAttributeIconSize 0
skinparam monochrome false
skinparam class {
    BackgroundColor #0f172a
    BorderColor #3b82f6
    FontColor #f1f5f9
    ArrowColor #06b6d4
}

abstract class Persona {
    # id: UUID
    # identificacion: String
    # nombreCompleto: String
    # emailInstitucional: String
    + getEmail(): String
}

class Estudiante {
    - codigoMatricula: String
    - promedioAcumulado: Double
    + solicitarInscripcion(asignatura: Asignatura): Boolean
}

class Docente {
    - tituloAcademico: String
    - horasSemanales: Integer
    + registrarCalificacion(estudiante: Estudiante, nota: Double): Void
}

class Matricula {
    - id: UUID
    - fechaCreacion: LocalDateTime
    - estado: EstadoMatricula
    - totalAranceles: BigDecimal
    + calcularTotal(): BigDecimal
    + confirmarPago(): Void
}

class DetalleMatricula {
    - id: UUID
    - costoMateria: BigDecimal
    - calificacionFinal: Double
}

class Asignatura {
    - codigo: String
    - nombre: String
    - creditos: Integer
    + validarCupo(): Boolean
}

enum EstadoMatricula {
    PENDIENTE
    PAGADA
    CANCELADA
}

Persona <|-- Estudiante : Generalización
Persona <|-- Docente : Generalización
Estudiante "1" -- "0..*" Matricula : Realiza >
Matricula "1" *-- "1..*" DetalleMatricula : Composición (Fuerte)
DetalleMatricula "0..*" -- "1" Asignatura : Asocia >
Matricula ..> EstadoMatricula : Usa
@enduml
