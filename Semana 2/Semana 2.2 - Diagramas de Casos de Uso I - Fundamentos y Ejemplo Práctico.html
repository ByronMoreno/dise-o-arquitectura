1 ¿Qué es un Diagrama de Casos de Uso según Píldoras Informáticas?

El diagrama de comportamiento más popular para negociar requisitos con el cliente

Como explica Juan Díaz en el vídeo, los diagramas de casos de uso pertenecen a los diagramas de comportamiento de UML. Tienen como meta fundamental responder a la pregunta: "¿Qué debe hacer el sistema para satisfacer a sus usuarios?" sin entrar en detalles de cómo se programará internamente (visión de caja negra).

1. El Límite del Sistema (System Boundary)

Representado por un rectángulo rotulado en la parte superior con el nombre del software. Delimita qué funcionalidades están dentro del alcance del desarrollo y qué elementos quedan fuera en el entorno exterior.

2. Los Actores (Actors)

Entidades externas que interactúan con el sistema. Se ubican siempre fuera del rectángulo del sistema y se representan comúnmente con la figura de palo (*stickman*). No representan personas individuales, sino roles.

3. Los Casos de Uso (Use Cases)

Representados por óvalos / elipses ubicados dentro del límite del sistema. Describen una secuencia de acciones que el software realiza y que produce un resultado observable de valor para un actor.

2 Tipología Completa de Actores en UML

Píldoras Informáticas destaca que un actor NO siempre es un ser humano

Tipo de Actor Descripción Conceptual Ejemplo en la App de Transporte Notación UML
Usuarios Humanos Primarios Personas que usan directamente el software para obtener el valor central de negocio. Pasajero: Solicita un viaje y paga.
Conductor: Acepta viajes y transporta.		 Figura de palo (*stickman*) o clase <<actor>>
Usuarios Humanos Secundarios / Admin Personal operativo que gestiona, supervisa, audita o mantiene la plataforma. Administrador: Da de alta vehículos, fija tarifas base y revisa reportes. Figura de palo (*stickman*)
Sistemas Informáticos Externos Servidores, bases de datos externas o APIs de terceros con las que nuestro sistema dialoga. Pasarela de Pagos (Stripe / Banco): Procesa el cobro de la tarjeta. Rectángulo con estereotipo <<system>> o *stickman*
Dispositivos Hardware / Sensores Hardware periférico que emite o recibe información técnica hacia el sistema. Sensor Satelital GPS: Emite coordenadas geográficas de latitud/longitud en tiempo real. Clase con estereotipo <<device>> o *stickman*
El Reloj / Temporizadores (Timer) Procesos temporales que disparan acciones automáticas por calendario o cron job. Timer de Cancelación: Si un conductor no responde en 60 segundos, reasigna el viaje. Icono de reloj o estereotipo <<timer>>

3 Caso Práctico del Vídeo: "App de Movilidad y Transporte Urbano"

Desarrollo paso a paso del caso presentado por Juan Díaz

En el vídeo se analiza una plataforma de transporte urbano (similar a Uber, Cabify o DiDi). A continuación se desglosa el modelado sistemático:

Roles y Actores Identificados

  • Administrador: Rol con privilegios de gestión de configuración de flota.
  • Pasajero / Usuario: Quien solicita el servicio y se traslada.
  • Conductor / Chofer: Quien presta el servicio de movilidad con su vehículo.
  • Sistema GPS / Geolocalización (Externo): Provee las coordenadas satelitales.
  • Pasarela de Pagos (Externa): Procesa transacciones con tarjeta de crédito/débito.

Casos de Uso Principales Identificados

  • Establecer tipos de transporte (Auto estándar, Confort, Van, Moto).
  • Fijar precios y tarifas base (Precio por km, recargo nocturno).
  • Geolocalizar posición del usuario (Lectura satelital GPS).
  • Solicitar viaje en transporte (Selección de origen y destino).
  • Aceptar viaje asignado (Confirmación del conductor).
  • Procesar cobro del trayecto (Transacción con la pasarela bancaria).

4 Diagrama PlantUML Oficial del Caso del Vídeo

Código limpio y estructurado listo para renderizar en cualquier IDE o herramienta web

diagrama_transporte_pildoras.puml 
@startuml
left to right direction
skinparam actorStyle awesome
skinparam packageStyle rectangle
skinparam monochrome false

skinparam rectangle {
    BackgroundColor #0f172a
    BorderColor #3b82f6
    FontColor #f1f5f9
}

skinparam usecase {
    BackgroundColor #1e293b
    BorderColor #06b6d4
    FontColor #f1f5f9
    ArrowColor #38bdf8
}

actor "Administrador" as admin
actor "Pasajero / Usuario" as pasajero
actor "Conductor / Chofer" as conductor
actor "Sistema GPS Externo" as gps <<System>>
actor "Pasarela de Pagos" as pasarela <<System>>

rectangle "Aplicación de Gestión de Transporte Urbano" {
    usecase "CU01: Establecer Tipos de Transporte" as CU01
    usecase "CU02: Fijar Precios y Tarifas" as CU02
    usecase "CU03: Geolocalizar Posición del Usuario" as CU03
    usecase "CU04: Solicitar Viaje en Transporte" as CU04
    usecase "CU05: Aceptar Viaje Asignado" as CU05
    usecase "CU06: Iniciar y Finalizar Trayecto" as CU06
    usecase "CU07: Procesar Cobro de Tarifa" as CU07
    usecase "CU08: Calificar Conductor y Servicio" as CU08
}

' Asociaciones del Administrador
admin -- CU01
admin -- CU02

' Asociaciones del Pasajero
pasajero -- CU03
pasajero -- CU04
pasajero -- CU08

' Asociaciones del Conductor
conductor -- CU05
conductor -- CU06

' Interacciones con Sistemas Externos
CU03 -- gps
CU07 -- pasarela
CU04 -- pasarela
@enduml

5 Especificación Textual del Caso de Uso "Solicitar Viaje"

El estándar formal que complementa al óvalo gráfico

Ficha Técnica: CU-04 Solicitar Viaje en Transporte 
ID: CU-04
Nombre del Caso de Uso: Solicitar Viaje en Transporte Urbano
Actor Principal: Pasajero / Usuario
Actores Secundarios: Sistema GPS Externo, Conductor, Pasarela de Pagos
Precondición: El pasajero ha iniciado sesión en la app y el GPS del móvil está activo.
Flujo Principal (Camino Básico):
  1. El pasajero abre la pantalla de solicitud de servicio.
  2. El sistema consulta las coordenadas actuales con el Sistema GPS Externo (CU-03).
  3. El pasajero introduce la dirección de destino.
  4. El sistema calcula la distancia estimada, tiempo de llegada y tarifa base según el tipo de transporte.
  5. El pasajero selecciona el tipo de vehículo (Estándar, Confort, Van) y confirma la solicitud.
  6. El sistema busca conductores cercanos disponibles y envía la notificación de asignación.
  7. Un conductor acepta el viaje (CU-05).
  8. El sistema muestra al pasajero los datos del vehículo (placa, modelo) y tiempo de recogida.
Flujos Alternativos / Excepciones:
  4a. No hay cobertura de GPS:
      - El sistema solicita al usuario escribir manualmente su punto de partida.
  6a. Ningún conductor disponible en un radio de 5 km:
      - El sistema alerta: "No hay vehículos disponibles en este momento. Intenta en unos minutos".
Postcondición: El estado del viaje pasa a "ASIGNADO" y se bloquea temporalmente al conductor.

6 Errores Clásicos Explicados en el Vídeo

Prácticas erróneas que debes evitar en tus entregas académicas y proyectos

❌ Error 1: Poner los Actores DENTRO del Sistema

Los actores representan entidades externas al software. Dibujar al "Pasajero" o al "Administrador" dentro del rectángulo del sistema es un error conceptual grave de notación UML.

❌ Error 2: Confundir Pasos Internos con Casos de Uso

"Conectar a base de datos MySQL" o "Validar sintaxis de password" NO son casos de uso. Son pasos de implementación interna. Un caso de uso debe entregar un valor de negocio observable para el actor.

❌ Error 3: Nombrar Casos de Uso con Sustantivos

Nombrar un óvalo como "Transporte" o "Precios" es incorrecto. La regla estricta de nomenclatura es siempre Verbo en Infinitivo + Objeto Directo: "Establecer tipos de transporte", "Fijar precios".

❌ Error 4: Usar Flechas con Dirección en la Asociación Básica

En el nivel introductorio (Vídeo 5), la relación entre actor y caso de uso es una línea de asociación sólida continua sin flechas, ya que representa comunicación bidireccional entre el actor y el sistema.
