Robustez y Seguridad del Software

Aprende a estructurar un sistema de software tolerante a fallos mediante el manejo profesional de excepciones, el diseño de estrategias de logging y patrones de resiliencia. Además, analizaremos los pilares de la seguridad moderna (Autenticación, Autorización, tokens JWT) y las vulnerabilidades más críticas recopiladas por OWASP.

Objetivos de Aprendizaje

Al finalizar esta sesión de estudio, comprenderás y sabrás aplicar mecanismos defensivos esenciales para evitar caídas del servicio y resguardar los activos de información del negocio:

Gestionar

Modelar y programar el flujo de control de excepciones checked vs unchecked y configurar logs de auditoría estructurados.

Resiliar

Diseñar componentes altamente tolerantes a fallos transitorios utilizando patrones Circuit Breaker, Retries y Fallbacks.

Proteger

Estructurar mecanismos de Autenticación y Autorización utilizando el protocolo descentralizado JSON Web Tokens (JWT).

Asegurar

Reconocer las vulnerabilidades de seguridad web críticas descritas en el OWASP Top 10 y aplicar tácticas para su mitigación.

1. Control de Errores y Excepciones

El manejo de errores es una disciplina de diseño estructural. Su propósito es definir un comportamiento controlado del software cuando ocurren escenarios no nominales, evitando que la aplicación falle de forma catastrófica (crash) y proporcionando una respuesta útil al cliente.

Excepciones Verificadas (Checked)

Representan fallos recuperables fuera del control de la aplicación (ej. archivo no encontrado, error de red). Obligan al desarrollador a declararlas o capturarlas de forma explícita en tiempo de compilación.

Excepciones No Verificadas (Runtime/Unchecked)

Generalmente representan fallos de programación o lógica interna (ej. NullPointerException, IndexOutOfBoundsException). Ocurren en tiempo de ejecución y no requieren una declaración explícita forzada.

Buenas Prácticas Arquitectónicas: Centralización del manejo de excepciones. En lugar de plagar el código de bloques try-catch duplicados, se implementan manejadores globales que interceptan fallos y formatean respuestas homogéneas: 

@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleUserNotFound(UserNotFoundException ex) {
        ErrorResponse err = new ErrorResponse("NOT_FOUND", ex.getMessage(), System.currentTimeMillis());
        return new ResponseEntity<>(err, HttpStatus.NOT_FOUND);
    }
    
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleFallback(Exception ex) {
        ErrorResponse err = new ErrorResponse("INTERNAL_ERROR", "Ha ocurrido un error inesperado", System.currentTimeMillis());
        return new ResponseEntity<>(err, HttpStatus.INTERNAL_SERVER_ERROR);
    }
}

2. Logging

El registro de eventos (Logging) es el diario de vida de una aplicación en ejecución. Permite a los arquitectos e ingenieros inspeccionar el estado del sistema, auditar transacciones clave y diagnosticar fallos en producción sin alterar el código ni interrumpir la ejecución.

3. Tolerancia a Fallos

En las arquitecturas distribuidas modernas (como microservicios), los fallos de red o de sistemas externos son inevitables. La Tolerancia a Fallos consiste en diseñar software que resista fallas en sus componentes subordinados sin colapsar por completo, utilizando mecanismos de autocuración.

Circuit Breaker (Disyuntor)

Detiene el flujo de peticiones hacia un servicio fallido de inmediato para evitar la sobrecarga y el agotamiento de hilos (thread starvation) en el cliente.

Retry (Reintento)

Vuelve a enviar automáticamente peticiones fallidas asumiendo que el error es temporal (ej. latencia de red) aplicando demoras exponenciales.

Fallback (Alternativa)

Mecanismo de escape para entregar una respuesta degradada pero útil en lugar de propagar un error de excepción (ej. recuperar datos de la caché).

El flujo de peticiones transcurre normalmente. El circuito monitorea el porcentaje de llamadas fallidas. Si el ratio supera el umbral configurado (ej. 50% de fallos en 10 segundos), el circuito cambiará automáticamente al estado ABIERTO para proteger al cliente.

4. Seguridad: Autenticación, Autorización y JWT

La seguridad del software asegura que únicamente los agentes adecuados accedan a la información correspondiente. Distinguimos dos fases clave: la Autenticación (validar la identidad, ¿quién eres?) y la Autorización (validar privilegios, ¿qué puedes hacer?).

Autenticación

El proceso en el cual el usuario proporciona credenciales válidas (password, huella, etc.). El sistema las valida y emite un token de sesión firmado.

Autorización

Ocurre después de autenticarse. El sistema lee el token y valida si el rol del usuario (ej. ROLE_USER, ROLE_ADMIN) tiene permisos para ejecutar la acción solicitada.

Especifica el tipo de token y el algoritmo de firma criptográfica utilizado.

2. PAYLOAD (Carga de Datos)

{
  "sub": "1234567890",
  "name": "Ana Gomez",
  "roles": ["ROLE_ADMIN"],
  "iat": 1516239022
}

Contiene los 'claims' o afirmaciones (datos del usuario y sus permisos de acceso).

3. VERIFY SIGNATURE (Firma Criptográfica)

HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  "tu_clave_secreta_super_segura_32_bytes"
)

La firma sirve para validar que el token no ha sido modificado en el camino. Se genera concatenando el header y payload codificados en Base64, aplicando la firma con una clave secreta que solo el servidor de backend conoce. Si alguien cambia tan solo un carácter del payload, la firma calculada no coincidirá y el servidor rechazará la petición.

5. OWASP Top 10

El proyecto de seguridad en aplicaciones web abiertas (OWASP) es una fundación mundial que publica de manera periódica el estándar de concientización sobre seguridad web. Este documento identifica las 10 categorías de vulnerabilidades más críticas que amenazan a las aplicaciones de software.

A01:2021

Broken Access Control (Control de Acceso Roto)

Ocurre cuando el software no restringe correctamente las acciones que pueden realizar los usuarios autenticados. Como consecuencia, atacantes pueden acceder a cuentas ajenas, visualizar archivos confidenciales o ejecutar privilegios administrativos inapropiados.

Escenario de Riesgo

Un usuario accede a su perfil mediante la URL '/api/usuarios/50'. Simplemente alterando el parámetro id a '/api/usuarios/51' puede visualizar y modificar la información confidencial de otro usuario sin validación de pertenencia.

Mitigación Recomendada

Denegar accesos por defecto (Principio de Menor Privilegio). Implementar validaciones a nivel de servidor que comprueben que el ID del token JWT coincida con el registro solicitado antes de retornar cualquier dato.
