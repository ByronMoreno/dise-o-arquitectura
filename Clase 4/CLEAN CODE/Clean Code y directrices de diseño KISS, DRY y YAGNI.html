Clean Code y directrices de diseño: KISS, DRY y YAGNI

No basta con escribir código que funcione y pase pruebas unitarias; debemos escribir software que cualquier miembro del equipo pueda leer, razonar, mantener y evolucionar sin fricción. Estudiamos los fundamentos de Clean Code, el principio de simplicidad radical (KISS), la no-duplicación de conocimiento (DRY) y el rechazo a la especulación prematura (YAGNI).

💡 Axioma Fundamental: "Cualquier tonto puede escribir código que una computadora entienda. Los buenos programadores escriben código que los humanos pueden entender." — Martin Fowler.

✨ 1. ¿Qué es Clean Code?

Clean Code significa escribir código que sea fácil de leer, comprender, probar y mantener. Imagina que desarrollas una aplicación con Java y Spring Boot. El programa funciona perfectamente, pero después de seis meses otro desarrollador debe modificarlo. Si necesita varias horas para entender qué hace cada método, probablemente existe una severa deuda de calidad en el diseño.

❌ Paso 1: Identificar el problema — Nombres crípticos y tipos inadecuados Código Antipatrón
ProductoService.java (Versión problemática) 
public class ProductoService {

    // ¿Qué es p? ¿Qué es d? ¿Qué significa x?
    public double calcular(double p, double d) {

        double x = p - (p * d / 100);

        return x;
    }
}

🚨 Diagnóstico del Código Incorrecto:

  • • Nombres crípticos: Las variables p, d y x no revelan su intención ni su dominio.
  • • Nombre de método genérico: calcular() no especifica qué calcula (¿un área, un impuesto, un descuento, un promedio?).
  • • Riesgo de precisión financiera: Utilizar tipos primitivos de coma flotante (double) para cálculos monetarios introduce errores de redondeo IEEE 754 inaceptables en contabilidad.
  • • Fricción cognitiva: Quien lea este método debe detenerse a descifrar la fórmula matemática para inferir su propósito de negocio.
✅ Paso 2: Aplicar Clean Code — Claridad semántica, tipos de alta precisión y Spring Boot Código Limpio
ProductoService.java (Versión Refactorizada) 
package com.tienda.service;

import org.springframework.stereotype.Service;
import java.math.BigDecimal;

@Service
public class ProductoService {

    public BigDecimal calcularPrecioConDescuento(
            BigDecimal precioBase,
            BigDecimal porcentajeDescuento) {

        if (precioBase.signum() < 0 || porcentajeDescuento.signum() < 0) {
            throw new IllegalArgumentException("Los valores monetarios y porcentajes no pueden ser negativos");
        }

        BigDecimal factorCien = BigDecimal.valueOf(100);
        BigDecimal montoDescuento = precioBase
                .multiply(porcentajeDescuento)
                .divide(factorCien, 2, java.math.RoundingMode.HALF_UP);

        return precioBase.subtract(montoDescuento);
    }
}

✨ Beneficios de la Refactorización:

  • ✓ Nombres autoexplicativos: precioBase, porcentajeDescuento y montoDescuento comunican la lógica sin necesidad de comentarios.
  • ✓ Propósito evidente: calcularPrecioConDescuento deja claro el objetivo del método.
  • ✓ Precisión monetaria: Uso estricto de BigDecimal con modo de redondeo RoundingMode.HALF_UP.
  • ✓ Componente gestionado: Anotado como @Service listo para inyección de dependencias en el ecosistema Spring.

📋 1.1 Principales Directrices de Clean Code

Clean Code no es una regla rígida ni escribir menos líneas a costa de la legibilidad. Es una disciplina orientada a hacer que la intención del autor resulte cristalina para cualquier lector.

Directriz Recomendación Profesional Buenas Prácticas en Java / Spring
Nombres Descriptivos Utilizar nombres que revelen la intención, sin abreviaturas crípticas ni desinformación. buscarPedidoPorClienteId() en vez de get() o find().
Métodos Pequeños Cada método debe tener una única responsabilidad y un único nivel de abstracción (SLAP). Métodos de 5 a 15 líneas; delegar suboperaciones a métodos privados semánticos.
Evitar Duplicación No repetir la misma lógica de negocio en múltiples servicios o capas de la aplicación. Extraer lógica reutilizable a servicios de dominio o utilitarios testeables.
Comentarios Útiles Explicar el porqué de una decisión no obvia, nunca repetir lo que ya expresa el código. Evitar comentarios obvios como // Incrementa i en 1.
Manejo de Excepciones Gestionar errores con excepciones de dominio tipadas en lugar de retornar null o códigos numéricos. Utilizar @RestControllerAdvice y @ExceptionHandler en Spring.
Organización por Capas Separar claramente la recepción HTTP (Controllers), la orquestación (Services) y el almacenamiento (Repositories). Arquitectura por capas limpia desacoplada mediante DTOs.
Código Consistente Mantener las mismas convenciones de nomenclatura (camelCase, PascalCase) y orden estructural en todo el proyecto. Configurar herramientas como Checkstyle, SonarLint o Spotless en Gradle/Maven.
📌 Regla de Oro: "Clean Code no significa escribir menos líneas. Significa escribir código cuyo propósito sea evidente."
KISS

Keep It Simple, Stupid — Manténlo Simple

"La solución más sencilla que cumple correctamente el requisito suele ser la mejor."

KISS nos invita a combatir la sobreingeniería. No debemos complicar una solución solamente porque dominamos patrones avanzados, capas abstractas o arquitecturas complejas. Un sistema simple es más fácil de depurar, más rápido de probar y drásticamente menos propenso a errores.

❌ Paso 1: Identificar el problema — Sobreingeniería extrema para calcular un IVA Antipatrón de Sobrecomplejidad
CalculadoraIVA.java (5 capas innecesarias para una multiplicación) 
public class CalculadoraIVA {

    // ❌ Cadena de llamadas que añade 4 métodos, 1 clase envoltorio y 0 valor de negocio
    public double calcularIVA(double precio) {
        return procesarOperacion(
            crearContexto(
                obtenerConfiguracion(
                    validarPrecio(precio)
                )
            )
        );
    }

    private double validarPrecio(double precio) {
        if (precio < 0) {
            throw new IllegalArgumentException();
        }
        return precio;
    }

    private double obtenerConfiguracion(double precio) {
        return 0.15; // Tasa fija del 15%
    }

    private Contexto crearContexto(double iva) {
        return new Contexto(iva);
    }

    private double procesarOperacion(Contexto contexto) {
        // ¡Ni siquiera multiplica por el precio base! Error grave escondido en la complejidad
        return contexto.getIva();
    }
}

🚨 Problemas de esta Implementación:

  • • Arquitectura astronauta: Crea clases de contexto y cascadas de métodos que aumentan la pila de ejecución para una operación elemental.
  • • Bugs ocultos por la complejidad: Debido al laberinto de métodos, el autor olvidó multiplicar por el precio, retornando únicamente 0.15 en lugar de precio * 0.15.
  • • Pesadilla para testing: Para probar una multiplicación se requeriría configurar mocks o recorrer 5 métodos privados.
✅ Paso 2: Aplicar KISS — Solución directa, legible y precisa Solución Simple y Efectiva
CalculadoraIVA.java (Versión Spring Boot limpia) 
package com.tienda.service;

import org.springframework.stereotype.Service;
import java.math.BigDecimal;

@Service
public class CalculadoraIVA {

    private static final BigDecimal TASA_IVA = new BigDecimal("0.15");

    public BigDecimal calcularIVA(BigDecimal precio) {
        if (precio == null || precio.signum() < 0) {
            throw new IllegalArgumentException("El precio debe ser un valor no nulo y positivo");
        }

        return precio.multiply(TASA_IVA);
    }
}

✨ ¿Qué ganamos con KISS?

  • ✓ Cero capas artificiales: La lógica se lee en 3 líneas de código claro.
  • ✓ Pruebas unitarias triviales: Se comprueba con un solo test assert BigDecimal(15) == calculadora.calcularIVA(BigDecimal(100)).
  • ✓ Menor probabilidad de errores: Al no haber convolución de flujo, los defectos no tienen dónde esconderse.
💡 ¿Cuándo aplicar KISS? Antes de crear una nueva interfaz, un factory o un patrón de diseño, pregúntate: "¿Estoy complicando innecesariamente una solución que se resuelve con un método directo?" Por ejemplo, no necesitas microservicios ni colas Kafka para una aplicación con 50 usuarios diarios que opera perfectamente como monolito modular.
DRY

Don't Repeat Yourself — No te Repitas

"Cada conocimiento o regla de negocio debe tener una representación única y autorizada dentro del sistema."

DRY fue formulado por Andy Hunt y Dave Thomas en The Pragmatic Programmer. No trata simplemente sobre no duplicar texto o líneas mecánicas de código; trata sobre no duplicar lógica de negocio, políticas o conocimiento. Si una regla cambia, debe modificarse en un solo lugar.

❌ Paso 1: Identificar el problema — Regla de descuento dispersa y copiada en múltiples clases Duplicación de Lógica
ClienteService.java y ClienteVipService.java (Fórmula idéntica copiada y pegada) 
// En ClienteService.java
@Service
public class ClienteService {
    public double calcularDescuento(double precio) {
        // ❌ Fórmula copiada manualmente: precio - (precio * tasa)
        return precio - (precio * 0.10);
    }
}

// En ClienteVipService.java
@Service
public class ClienteVipService {
    public double calcularDescuento(double precio) {
        // ❌ Misma fórmula duplicada con diferente porcentaje
        return precio - (precio * 0.20);
    }
}

🚨 Peligros de la Duplicación:

  • • Inconsistencias silenciosas: Si mañana la directiva estipula que el descuento aplica sobre el precio neto antes de impuestos o que se redondea hacia arriba, se debe buscar en decenas de archivos. Si uno se olvida, el sistema cobrará distinto según el cliente.
  • • Riesgo de Copy-Paste: Copiar fragmentos de código tiende a replicar defectos y malas prácticas a lo largo de toda la base de código.
✅ Paso 2: Aplicar DRY — Servicio centralizado con Inyección de Dependencias Fuente Única de Verdad
CalculadoraDescuento.java + Inyección en Clientes (Spring Boot) 
// 1. Componente de Dominio Centralizado
@Service
public class CalculadoraDescuento {

    public BigDecimal calcular(BigDecimal precio, BigDecimal porcentaje) {
        if (precio == null || porcentaje == null) {
            throw new IllegalArgumentException("Los parámetros no pueden ser nulos");
        }
        BigDecimal montoDescuento = precio.multiply(porcentaje);
        return precio.subtract(montoDescuento);
    }
}

// 2. Cliente Estándar: Sólo aporta el conocimiento de su tasa (10%)
@Service
@RequiredArgsConstructor
public class ClienteService {

    private static final BigDecimal DESCUENTO_ESTANDAR = new BigDecimal("0.10");
    private final CalculadoraDescuento calculadora;

    public BigDecimal calcularDescuento(BigDecimal precio) {
        return calculadora.calcular(precio, DESCUENTO_ESTANDAR);
    }
}

// 3. Cliente VIP: Sólo aporta el conocimiento de su tasa (20%)
@Service
@RequiredArgsConstructor
public class ClienteVipService {

    private static final BigDecimal DESCUENTO_VIP = new BigDecimal("0.20");
    private final CalculadoraDescuento calculadora;

    public BigDecimal calcularDescuento(BigDecimal precio) {
        return calculadora.calcular(precio, DESCUENTO_VIP);
    }
}

✨ ¿Qué ganamos con DRY?

  • ✓ Fórmula centralizada: La regla matemática de deducción de descuento existe en un único método verificable.
  • ✓ Mantenimiento en un paso: Modificar la política de cálculo impacta inmediatamente a clientes estándar, VIP y cualquier futuro segmento.
  • ✓ Acoplamiento sano: Los servicios delegan el trabajo técnico a un componente reutilizable mediante @RequiredArgsConstructor de Lombok.
⚠️ Ojo con el falso DRY: No toda coincidencia de código debe unificarse a la fuerza. Dos métodos pueden tener líneas similares pero representar reglas de negocio totalmente independientes que evolucionarán a ritmos distintos. Unificar código prematuramente puede crear acoplamiento indeseado.
YAGNI

You Aren't Gonna Need It — No vas a Necesitarlo

"No desarrolles funcionalidades que todavía no han sido solicitadas ni justificadas por el negocio."

Los desarrolladores a menudo caen en la tentación de programar características "por si acaso" en el futuro. El resultado: código que consume tiempo de desarrollo, cuesta dinero de mantenimiento, genera errores colaterales y en la gran mayoría de casos nunca se llega a utilizar.

❌ Paso 1: Identificar el problema — Entidad inflada con características hipotéticas Especulación Prematura
Producto.java (Requisito real: id, nombre, precio, stock. Desarrollador: ¡IA y logística global!) 
@Entity
public class Producto {

    @Id
    private Long id;
    private String nombre;
    private BigDecimal precio;
    private Integer stock;

    // ❌ FUNCIONALIDADES NUNCA SOLICITADAS POR EL CLIENTE:
    private BigDecimal precioFuturo;
    private String prediccionVentas;
    private String recomendacionIA;
    private String proveedorInternacional;
    private String historialPrecios;
    private Boolean soporteCriptomonedas;
    private Double pesoAduaneroParaDrones;
}

🚨 Consecuencias de Violar YAGNI:

  • • Costo de desarrollo desperdiciado: Horas de diseño de tablas, migraciones Liquibase/Flyway y validaciones para atributos sin uso.
  • • Deuda cognitiva: Cualquier programador nuevo se preguntará: "¿Dónde se llena prediccionVentas? ¿Por qué siempre viene en null?".
  • • Bloqueo de cambios futuros: Cuando el cliente pida un modelo real de recomendaciones, el código especulativo existente estorbará y obligará a hacer refactorizaciones complejas.
✅ Paso 2: Aplicar YAGNI — Desarrollar únicamente el valor que el negocio demanda hoy Código Just-In-Time
Producto.java y ProductoService.java (Enfoque enfocado y pragmático) 
@Entity
@Getter @Setter @NoArgsConstructor @AllArgsConstructor
public class Producto {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @NotBlank(message = "El nombre es obligatorio")
    private String nombre;

    @NotNull @Positive
    private BigDecimal precio;

    @NotNull @PositiveOrZero
    private Integer stock;
}

// Servicio enfocado en los casos de uso solicitados
@Service
@RequiredArgsConstructor
public class ProductoService {

    private final ProductoRepository repository;

    public Producto registrar(Producto producto) {
        return repository.save(producto);
    }

    public List<Producto> listar() {
        return repository.findAll();
    }
}

✨ ¿Qué ganamos con YAGNI?

  • ✓ Entrega rápida de valor: El producto llega a producción en días en lugar de meses.
  • ✓ Claridad absoluta: Cada propiedad y método del código tiene un propósito actual demostrable.
  • ✓ Flexibilidad para el cambio: Cuando surja la necesidad real de IA o predicción de ventas, se diseñará con los requisitos verdaderos de ese momento, no con suposiciones obsoletas.

⚖️ 5. Comparación de KISS, DRY y YAGNI

Los tres principios persiguen un objetivo común: mantener la base de código limpia, sostenible y barata de mantener. Sin embargo, cada uno combate un enemigo diferente de la ingeniería de software:

KISS
Simplicidad Esencial

Combate la complejidad innecesaria y la sobreingeniería. Promueve que la solución directa y legible siempre derrota a estructuras abstractas redundantes.

❓ Pregunta Clave: "¿Puedo resolver esto de una manera más simple y directa?"
DRY
No Duplicación

Combate la dispersión de reglas de negocio. Garantiza que cualquier conocimiento crítico posea una única fuente de verdad autorizada en el sistema.

❓ Pregunta Clave: "¿Estoy duplicando una regla de negocio que ya existe en otro lugar?"
YAGNI
Necesidad Real

Combate la especulación prematura y las features fantasma. Exige no codificar nada basándose en conjeturas de "quizá algún día lo usemos".

❓ Pregunta Clave: "¿Esta funcionalidad me fue solicitada hoy o la estoy inventando por especulación?"

🧩 6. ¿Cómo se relacionan con SOLID y GRASP?

Estos tres marcos no compiten entre sí; se potencian mutuamente. Clean Code, KISS, DRY y YAGNI aportan la filosofía y disciplina de desarrollo, mientras que SOLID y GRASP proporcionan la técnica de modelado de clases y responsabilidades.

Marco / Principio Propósito Principal Pregunta de Diseño Clave
Clean Code Garantizar legibilidad, intención clara y facilidad de prueba. ¿Un nuevo colega comprenderá este método en 30 segundos?
KISS Evitar sobreingeniería y capas innecesarias. ¿Es esta la solución más sencilla que cumple el requisito?
DRY Centralizar reglas de negocio y políticas del dominio. ¿Si cambia esta política, debo editar más de un archivo?
YAGNI Evitar construir código especulativo no solicitado. ¿El negocio solicitó formalmente esta funcionalidad hoy?
SOLID Diseñar clases desacopladas, extensibles y testeables. ¿Mis clases tienen una sola responsabilidad y dependen de abstracciones?
GRASP Asignar responsabilidades a los objetos adecuados. ¿Quién tiene la información necesaria para realizar esta tarea?

🛒 Ejemplo Integrado: Los 6 marcos colaborando en nuestra Tienda Virtual

Observa cómo se orquesta la creación y cálculo de un pedido cuando aplicamos todos los principios simultáneamente:

Clean Code: Nombres expresivos como calcularTotalPedido() en lugar de abreviaciones.
KISS: Suma directa de subtotales sin crear fábricas ni middlewares inventados.
DRY: El cálculo de subtotales se centraliza en DetallePedido, sin recalcularlo en controllers.
YAGNI: No implementamos predicción de compras con IA ni monedas virtuales si el cliente no las pidió.
SOLID: PedidoService coordina sin saber cómo se factura (SRP) e inyecta interfaces (DIP).
GRASP: Pedido calcula su propio total porque es el Information Expert que posee los productos.

8. Actividad Práctica: Refactorización de Código

Taller de Ingeniería de Software para refactorizar código heredado con deuda técnica.

Escenario: Una tienda virtual heredó el siguiente servicio llamado TiendaService. El código funciona en producción, pero presenta serios problemas de arquitectura y calidad de código:

TiendaService.java (Código Inicial con Deuda Técnica) 
@Service
public class TiendaService {

    public double calcular(double p) {
        return p - (p * 0.10);
    }

    public double calcularVip(double p) {
        return p - (p * 0.20);
    }

    public void registrar(double p) {
        System.out.println("Registrando: " + p);
    }

    public void enviar(double p) {
        System.out.println("Enviando correo: " + p);
    }
}

📋 Desafío para los Estudiantes:

  • 1. Identificar problemas de Clean Code: Nombres como p, calcular(), uso de double para finanzas e impresiones con System.out.println en vez de Logging.
  • 2. Identificar duplicación de código: La fórmula matemática p - (p * tasa) está duplicada en dos métodos.
  • 3. Aplicar DRY: Centralizar la fórmula de cálculo de descuentos en un servicio reutilizable.
  • 4. Aplicar KISS: Simplificar los métodos y evitar estructuras innecesarias.
  • 5. Separar responsabilidades (SRP / Clean Code): Separar la lógica financiera de la persistencia y de la notificación por correo.

✨ Solución Refactorizada en Spring Boot 3.5 con Java 21

Separamos las responsabilidades en componentes cohesivos y aplicamos tipos financieros seguros (BigDecimal) junto a Logging profesional (Slf4j):

1. CalculadoraDescuentoService.java (Aplica DRY y Clean Code) 
@Service
public class CalculadoraDescuentoService {

    public BigDecimal aplicarDescuento(BigDecimal precioBase, BigDecimal tasaDescuento) {
        if (precioBase == null || tasaDescuento == null) {
            throw new IllegalArgumentException("El precio base y la tasa no pueden ser nulos");
        }
        BigDecimal descuento = precioBase.multiply(tasaDescuento);
        return precioBase.subtract(descuento);
    }
}
2. NotificacionService.java y VentaService.java (Separación de Responsabilidades) 
@Service
@Slf4j
public class NotificacionService {
    public void notificarConfirmacion(String destinatario, BigDecimal monto) {
        log.info("Enviando correo de confirmación a {} por monto: {}", destinatario, monto);
    }
}

@Service
@RequiredArgsConstructor
public class TiendaService {

    private static final BigDecimal TASA_REGULAR = new BigDecimal("0.10");
    private static final BigDecimal TASA_VIP = new BigDecimal("0.20");

    private final CalculadoraDescuentoService calculadoraDescuento;
    private final NotificacionService notificacionService;

    public BigDecimal calcularPrecioRegular(BigDecimal precio) {
        return calculadoraDescuento.aplicarDescuento(precio, TASA_REGULAR);
    }

    public BigDecimal calcularPrecioVip(BigDecimal precio) {
        return calculadoraDescuento.aplicarDescuento(precio, TASA_VIP);
    }
}
