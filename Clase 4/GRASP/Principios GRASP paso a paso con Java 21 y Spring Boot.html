Principios GRASP paso a paso con Java 21 y Spring Boot

Si SOLID nos ayuda a diseñar clases limpias y dependencias desacopladas, GRASP nos ayuda a responder la pregunta fundamental del diseño orientado a objetos: "¿Qué clase debe encargarse de cada responsabilidad dentro del sistema?"

💡 Definición Clave: GRASP significa General Responsibility Assignment Software Patterns (patrones generales para asignar responsabilidades al software). Fueron propuestos por Craig Larman y son esenciales para estructurar arquitecturas empresariales por capas con Spring Boot y Spring Data JPA.

01

Information Expert (Experto en Información)

"Asignar la responsabilidad a la clase que tiene la información necesaria para cumplirla."

Si un cálculo o decisión requiere los datos de una entidad, es esa entidad la que debe poseer el método que ejecuta la operación, evitando extraer los datos hacia capas externas.

❌ Paso 1: Identificar el Problema (Cálculo indebido en el Controlador) Código Incorrecto
PedidoController.java calculando el total manualmente 
@RestController
@RequestMapping("/pedidos")
public class PedidoController {

    @PostMapping("/total")
    public double calcularTotal(@RequestBody Pedido pedido) {
        double total = 0;
        // ❌ El controlador viola Information Expert al extraer datos e iterar manualmente
        for (Producto producto : pedido.getProductos()) {
            total += producto.getPrecio() * producto.getCantidad();
        }
        return total;
    }
}
¿Qué problemas genera? El controlador asume lógica matemática de negocio. Si un servicio de facturación, un reporte o una tarea batch necesita el total, tendrán que duplicar el mismo bucle for en cada lugar.
✅ Paso 2: Aplicar la Solución (Pedido y DetallePedido son los expertos) Diseño Refactorizado
1. DetallePedido.java (Experto en subtotal: precio x cantidad) 
@Entity
public class DetallePedido {
    @ManyToOne
    private Producto producto;
    private Integer cantidad;

    // ✅ Experto en calcular su propio subtotal
    public BigDecimal calcularSubtotal() {
        return producto.getPrecio()
                .multiply(BigDecimal.valueOf(cantidad));
    }
}
2. Pedido.java (Experto en sumar subtotales de sus detalles) 
@Entity
public class Pedido {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(cascade = CascadeType.ALL)
    private List<DetallePedido> detalles = new ArrayList<>();

    // ✅ Experto en el total completo del pedido
    public BigDecimal calcularTotal() {
        return detalles.stream()
                .map(DetallePedido::calcularSubtotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}
3. PedidoController.java (Solo delega al experto) 
@GetMapping("/{id}/total")
public BigDecimal calcularTotal(@PathVariable Long id) {
    Pedido pedido = pedidoService.buscarPorId(id);
    return pedido.calcularTotal(); // ✅ Limpio y reutilizable
}
🔍
¿Cómo diagnosticar una violación de Information Expert?

Pregúntate: "¿Qué clase tiene los campos y datos necesarios para realizar esta operación?" Si una clase externa está haciendo múltiples get() para sumar o procesar datos de otra entidad, traslada el método directamente a la clase poseedora de los datos.

02

Creator (Creador)

"Asignar la responsabilidad de crear una instancia de la clase A a la clase B si B contiene, agrega, graba o utiliza estrechamente a A."

❌ Paso 1: Identificar el Problema (Controlador creando manualmente partes internas) Código Incorrecto
El controlador construye pieza a pieza los detalles de la compra 
@PostMapping
public Pedido crearPedido(@RequestBody PedidoRequest request) {
    Pedido pedido = new Pedido();

    for (ItemRequest item : request.items()) {
        // ❌ El controlador se encarga de instanciar DetallePedido
        DetallePedido detalle = new DetallePedido();
        detalle.setCantidad(item.cantidad());
        detalle.setProducto(productoService.buscarPorId(item.productoId()));
        pedido.getDetalles().add(detalle);
    }
    return pedidoService.guardar(pedido);
}
✅ Paso 2: Aplicar la Solución (Pedido crea y encapsula sus propios detalles) Diseño Refactorizado
Pedido.java (Creador natural de DetallePedido) 
@Entity
public class Pedido {
    @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)
    private List<DetallePedido> detalles = new ArrayList<>();

    // ✅ Pedido crea y administra el ciclo de vida de DetallePedido
    public void agregarDetalle(Producto producto, Integer cantidad) {
        DetallePedido detalle = new DetallePedido(producto, cantidad);
        detalles.add(detalle);
    }
}
PedidoService.java (Orquesta invocando al método Creador) 
@Service
@RequiredArgsConstructor
public class PedidoService {
    private final PedidoRepository pedidoRepository;
    private final ProductoRepository productoRepository;

    public Pedido crear(PedidoRequest request) {
        Pedido pedido = new Pedido();
        for (ItemRequest item : request.items()) {
            Producto producto = productoRepository.findById(item.productoId()).orElseThrow();
            pedido.agregarDetalle(producto, item.cantidad()); // ✅ Creación centralizada
        }
        return pedidoRepository.save(pedido);
    }
}
🔍
¿Cómo diagnosticar una violación de Creator?

Pregúntate: "¿Qué objeto contiene, almacena o tiene la información de inicialización de la entidad que quiero instanciar?" Si estás instanciando componentes hijos desde controladores o servicios distantes, mueve el método creador al contenedor directo.

03

Controller (Controlador)

"Asignar la responsabilidad de recibir o gestionar un mensaje de evento del sistema a una clase que represente el sistema global o el escenario de caso de uso."

❌ Paso 1: Identificar el Problema (El controlador hace todo el trabajo) Código Incorrecto
Controlador hinchado con lógica de base de datos y negocio 
@RestController
@RequestMapping("/pedidos")
public class PedidoController {
    private final PedidoRepository repository;
    private final ProductoRepository productoRepository;

    @PostMapping
    public Pedido crear(@RequestBody PedidoRequest request) {
        // ❌ El controlador busca en BD, arma pedidos, calcula y notifica
        Pedido pedido = new Pedido();
        // Buscar productos... crear detalles... calcular totales... enviar emails...
        return repository.save(pedido);
    }
}
✅ Paso 2: Aplicar la Solución (Separar Endpoint HTTP de Caso de Uso) Diseño Refactorizado
PedidoController.java (Solo atiende HTTP y serialización) 
@RestController
@RequestMapping("/pedidos")
@RequiredArgsConstructor
public class PedidoController {
    private final PedidoService pedidoService;

    @PostMapping
    public ResponseEntity<Pedido> crear(@RequestBody PedidoRequest request) {
        Pedido pedido = pedidoService.crear(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(pedido);
    }
}
PedidoService.java (Controlador de Caso de Uso en Spring Boot) 
@Service
@RequiredArgsConstructor
public class PedidoService {
    private final PedidoRepository repository;

    public Pedido crear(PedidoRequest request) {
        // ✅ Coordina la orquestación del caso de uso de negocio
        return repository.save(new Pedido());
    }
}
🔍
¿Cómo diagnosticar una violación de Controller?

Pregúntate: "¿Mi controlador REST está ejecutando transacciones, consultas SQL o lógica algorítmica directamente?" Si es así, delega el caso de uso a un servicio (Application/Use Case Service) para que el controlador solo gestione el protocolo web.

04

Low Coupling (Bajo Acoplamiento)

"Asignar responsabilidades de forma que las dependencias entre clases se mantengan al mínimo posible."

❌ Paso 1: Identificar el Problema (Dependencia dura a clase concreta) Código Incorrecto
PedidoService atado directamente a EmailService 
@Service
public class PedidoService {
    // ❌ Acoplamiento rígido con new
    private final EmailService emailService = new EmailService();

    public void confirmarPedido() {
        emailService.enviar("Pedido confirmado");
    }
}
✅ Paso 2: Aplicar la Solución (Contrato abstracto Notificador) Diseño Refactorizado
Notificador.java e Implementaciones (@Service, @Primary) 
public interface Notificador { void enviar(String mensaje); }

@Service @Primary
public class EmailService implements Notificador {
    @Override public void enviar(String msg) { System.out.println("Correo: " + msg); }
}

@Service
public class WhatsAppService implements Notificador {
    @Override public void enviar(String msg) { System.out.println("WhatsApp: " + msg); }
}
PedidoService.java (Depende de la interfaz y no de la tecnología) 
@Service
@RequiredArgsConstructor
public class PedidoService {
    // ✅ Bajo acoplamiento mediante inversión de control
    private final Notificador notificador;

    public void confirmarPedido() {
        notificador.enviar("Pedido confirmado");
    }
}
🔍
¿Cómo diagnosticar una violación de Low Coupling?

Pregúntate: "Si modifico la implementación técnica de una clase, ¿cuántas otras clases se ven forzadas a cambiar o recompilarse?" Si el cambio se propaga en cascada, reduce las dependencias directas mediante abstracciones.

05

High Cohesion (Alta Cohesión)

"Asignar responsabilidades de forma que las tareas de una clase estén íntimamente relacionadas entre sí y enfocadas en un objetivo unificado."

❌ Paso 1: Identificar el Problema (SistemaService "Bolsa de Gatos") Código Incorrecto
SistemaService acumulando tareas inconexas 
@Service
public class SistemaService {
    public void crearPedido() { ... }
    public void enviarCorreo() { ... }
    public void generarFactura() { ... }
    public void registrarUsuario() { ... }
    public void generarReporte() { ... }
    public void calcularImpuestos() { ... }
}
✅ Paso 2: Aplicar la Solución (Servicios Altamente Cohesivos por Dominio) Diseño Refactorizado
PedidoService.java (Enfocado exclusivamente en el ciclo de vida del pedido) 
@Service
@RequiredArgsConstructor
public class PedidoService {
    private final PedidoRepository repository;

    public Pedido crear(Pedido pedido) { return repository.save(pedido); }
    public Pedido buscar(Long id) { return repository.findById(id).orElseThrow(); }
    public void cancelar(Long id) {
        Pedido pedido = buscar(id);
        pedido.cancelar();
        repository.save(pedido);
    }
}
// ✅ Cada servicio se enfoca en su área: UsuarioService, FacturaService, EmailService
🔍
¿Cómo diagnosticar una violación de High Cohesion?

Pregúntate: "¿Todos los métodos de esta clase colaboran directamente para cumplir un único objetivo de negocio?" Si la clase atiende dominios dispares (usuarios, pagos, PDFs, emails), divide la clase en componentes especializados.

06

Polymorphism (Polimorfismo)

"Cuando los comportamientos varían según el tipo, asignar la responsabilidad de la variación a los tipos para los que varía utilizando operaciones polimórficas."

❌ Paso 1: Identificar el Problema (Condicionales por tipo de envío) Código Incorrecto
EnvioService con if-else por tipo de tarifa 
@Service
public class EnvioService {
    public double calcularCosto(String tipo, double peso) {
        if (tipo.equals("NORMAL")) {
            return peso * 2;
        } else if (tipo.equals("EXPRESS")) {
            return peso * 5;
        } else if (tipo.equals("INTERNACIONAL")) {
            return peso * 10;
        }
        throw new IllegalArgumentException();
    }
}
✅ Paso 2: Aplicar la Solución (Estrategias Polimórficas Inyectadas en Map) Diseño Refactorizado
TipoEnvio.java y Componentes de Tarifa 
public interface TipoEnvio { BigDecimal calcularCosto(BigDecimal peso); }

@Component("normal")
public class EnvioNormal implements TipoEnvio {
    @Override public BigDecimal calcularCosto(BigDecimal p) { return p.multiply(BigDecimal.valueOf(2)); }
}

@Component("express")
public class EnvioExpress implements TipoEnvio {
    @Override public BigDecimal calcularCosto(BigDecimal p) { return p.multiply(BigDecimal.valueOf(5)); }
}
EnvioService.java (Inyección de Map<String, TipoEnvio> en Spring Boot) 
@Service
@RequiredArgsConstructor
public class EnvioService {
    // Spring inyecta automáticamente todos los beans usando el nombre del componente como clave
    private final Map<String, TipoEnvio> estrategias;

    public BigDecimal calcular(String tipo, BigDecimal peso) {
        TipoEnvio estrategia = estrategias.get(tipo.toLowerCase());
        if (estrategia == null) throw new IllegalArgumentException("Tipo de envío no válido");
        return estrategia.calcularCosto(peso);
    }
}
🔍
¿Cómo diagnosticar una violación de Polymorphism?

Pregúntate: "¿Estoy usando cadenas if/else o switch basadas en un atributo de tipo para decidir cómo ejecutar una lógica?" Reemplaza las ramas condicionales por implementaciones polimórficas de una interfaz común.

07

Pure Fabrication (Fabricación Pura)

"Asignar un conjunto altamente cohesivo de responsabilidades a una clase artificial que no representa un concepto del dominio del problema, con el fin de favorecer el bajo acoplamiento y la alta cohesión."

❌ Paso 1: Identificar el Problema (Entidad de negocio ensuciada con SQL) Código Incorrecto
Pedido.java administrando conexiones a PostgreSQL 
public class Pedido {
    // ❌ Mezcla lógica de negocio con infraestructura técnica
    public void guardarEnBaseDatos() {
        // Conexión JDBC... Preparar sentencia INSERT... Manejar SQLException...
    }

    public void calcularTotal() {
        // Lógica del negocio
    }
}
✅ Paso 2: Aplicar la Solución (Repositorios y DAOs como Fabricación Pura) Diseño Refactorizado
PedidoRepository.java (Clase técnica artificial en Spring Data JPA) 
// ✅ "PedidoRepository" no existe en la vida real (un cliente no compra repositorios)
// Es una FABRICACIÓN PURA para aislar la persistencia técnica sin manchar el dominio.
@Repository
public interface PedidoRepository extends JpaRepository<Pedido, Long> {
}

@Service
@RequiredArgsConstructor
public class PedidoService {
    private final PedidoRepository repository;

    public Pedido guardar(Pedido pedido) {
        return repository.save(pedido);
    }
}
🔍
¿Cómo diagnosticar una violación de Pure Fabrication?

Pregúntate: "¿Estoy forzando a una entidad de negocio a encargarse de serialización JSON, almacenamiento en disco, cifrado o conexiones de red?" Crea clases de fabricación pura (Repositories, Mappers, Adapters, Builders) para salvaguardar la pureza del dominio.

08

Indirection (Indirección)

"Asignar la responsabilidad a un objeto intermediario para mediar entre otros componentes o servicios, de modo que no queden acoplados directamente."

❌ Paso 1: Identificar el Problema (Acoplamiento directo con API externa) Código Incorrecto
PagoService llamando directamente al SDK de PayPal 
@Service
public class PagoService {
    public void pagar(double monto) {
        // ❌ Si cambiamos a Stripe o Redsys, PagoService colapsa y debe reescribirse
        PayPalApi api = new PayPalApi();
        api.realizarPago(monto);
    }
}
✅ Paso 2: Aplicar la Solución (Adaptador Intermediario) Diseño Refactorizado
PasarelaPago.java (Contrato de Indirección) y Adaptadores 
public interface PasarelaPago { void realizarPago(BigDecimal monto); }

@Component @Primary @RequiredArgsConstructor
public class PayPalAdapter implements PasarelaPago {
    private final PayPalApi payPalApi;
    @Override public void realizarPago(BigDecimal monto) { payPalApi.realizarPago(monto); }
}

@Component @RequiredArgsConstructor
public class StripeAdapter implements PasarelaPago {
    private final StripeApi stripeApi;
    @Override public void realizarPago(BigDecimal monto) { stripeApi.cobrar(monto); }
}
PagoService.java (Solo se comunica a través del intermediario) 
@Service
@RequiredArgsConstructor
public class PagoService {
    // ✅ Mediación por indirección
    private final PasarelaPago pasarelaPago;

    public void pagar(BigDecimal monto) {
        pasarelaPago.realizarPago(monto);
    }
}
🔍
¿Cómo diagnosticar una violación de Indirection?

Pregúntate: "¿Dos componentes que deberían ser independientes están acoplados directamente sin una capa intermedia que amortigüe los cambios?" Aplica el patrón Adapter o Facade para introducir un intermediario estabilizador.

09

Protected Variations (Variaciones Protegidas)

"Identificar los puntos de variación o inestabilidad previsibles y asignar responsabilidades para crear una interfaz estable alrededor de ellos."

❌ Paso 1: Identificar el Problema (Lógica de negocio expuesta a API de terceros inestable) Código Incorrecto
CompraService consultando directamente el precio del dólar 
@Service
public class CompraService {
    public BigDecimal convertirDolares(BigDecimal monto) {
        // ❌ Conexión directa a API externa de tipo de cambio.
        // Si el proveedor cambia su JSON o se cae, nuestro servicio de compras colapsa.
        return monto;
    }
}
✅ Paso 2: Aplicar la Solución (Contrato Blindado TipoCambioProvider) Diseño Refactorizado
TipoCambioProvider.java (Interfaz Estable) y Proveedores 
public interface TipoCambioProvider { BigDecimal obtenerTasaCambio(); }

@Service @Primary
public class BancoCentralProvider implements TipoCambioProvider {
    @Override public BigDecimal obtenerTasaCambio() { return BigDecimal.ONE; }
}

@Service
public class ProveedorExternoProvider implements TipoCambioProvider {
    @Override public BigDecimal obtenerTasaCambio() { return BigDecimal.ONE; }
}
CompraService.java (Blindado ante cualquier cambio de proveedor externo) 
@Service
@RequiredArgsConstructor
public class CompraService {
    // ✅ Variación protegida mediante contrato estable
    private final TipoCambioProvider tipoCambioProvider;

    public BigDecimal convertirDolares(BigDecimal monto) {
        BigDecimal tasa = tipoCambioProvider.obtenerTasaCambio();
        return monto.multiply(tasa);
    }
}
🔍
¿Cómo diagnosticar una violación de Protected Variations?

Pregúntate: "¿Qué partes del sistema son propensas a cambiar (APIs de terceros, formatos legales, pasarelas) y cómo protejo el resto de la aplicación?" Blinda esos puntos de dolor detrás de interfaces estables de tu propio dominio.

Tabla de Síntesis

⚖️ 11. Diferencia entre SOLID y GRASP

Comparación Arquitectónica

Una duda muy común entre los estudiantes: ¿Son rivales o compiten entre sí? ¡No, se complementan armónicamente!

Criterio SOLID GRASP
Naturaleza 5 principios de diseño orientado a objetos. 9 patrones para asignar responsabilidades.
Foco Primario Diseño de clases, herencia y gestión de dependencias. ¿Quién debe hacer qué? Asignación de roles.
Objetivo Mantener código flexible, extensible y testeable. Distribuir correctamente las responsabilidades en el modelo.
Momento de Uso Para refactorizar y mejorar la arquitectura técnica. Para tomar decisiones de diseño desde el modelo conceptual.

🌟 Ejemplo Práctico de Complementariedad al Construir un Pedido:

  • GRASP Information Expert: Te dice que Pedido debe calcular su propio total porque tiene los detalles.
  • GRASP Creator: Te dice que Pedido debe crear sus propios DetallePedido.
  • GRASP Controller: Te dice que PedidoService coordina el caso de uso y PedidoController atiende la web.
  • SOLID SRP: Evita que PedidoService acumule envío de correos y facturación en la misma clase.
  • SOLID DIP: Garantiza que el servicio dependa de la interfaz Notificador y no de una clase concreta.

Para asignaturas universitarias de Ingeniería de Software, esta secuencia pedagógica estructurada por semanas maximiza la retención y la aplicación práctica:

Sesión Principios GRASP Actividad Práctica Aplicada
Clase 1 Information Expert & Creator Diseñar el cálculo de totales y la creación de líneas de pedidos en el modelo de dominio.
Clase 2 Controller Construir una API REST en Spring Boot separando el Controlador HTTP del Caso de Uso.
Clase 3 Low Coupling & High Cohesion Refactorizar servicios monolíticos tipo "God Class" en componentes especializados.
Clase 4 Polymorphism Implementar pasarelas de pago y cotizadores de envíos con mapas de Beans inyectados.
Clase 5 Pure Fabrication & Indirection Implementar Repositorios JPA y adaptadores para servicios de terceros (PayPal / SendGrid).
Clase 6 Protected Variations Blindar integraciones con proveedores inestables (tasas de cambio / APIs de aduanas).

💡 Consejo Metodológico para el Aula:

Primero presenta el código incorrecto (el controlador calculando el total o la entidad Pedido con código SQL JDBC). Pregunta a tus estudiantes qué problemas de mantenimiento o testing encuentran. Cuando sientan el dolor del mal diseño, introduce el principio GRASP correspondiente como la solución elegante.

De este modo no memorizan definiciones teóricas: aprenden a tomar decisiones de arquitectura fundamentadas como ingenieros de software senior.
