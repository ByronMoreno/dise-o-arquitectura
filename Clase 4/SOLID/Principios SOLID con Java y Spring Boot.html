🧱 1. ¿Qué es SOLID?

Fundamentos de Diseño

SOLID es un acrónimo mnemotécnico acuñado por Robert C. Martin (Uncle Bob) que consolida cinco principios fundamentales para el diseño orientado a objetos:

S
SRP
Single Responsibility Principle (Responsabilidad Única)
O
OCP
Open/Closed Principle (Abierto / Cerrado)
L
LSP
Liskov Substitution Principle (Sustitución de Liskov)
I
ISP
Interface Segregation Principle (Segregación de Interfaces)
D
DIP
Dependency Inversion Principle (Inversión de Dependencias)
🛠️
Mantenibilidad

Localización inmediata de errores sin efectos colaterales imprevistos.

🧩
Extensibilidad

Adición de nuevas funcionalidades empresariales sin reescribir código previo.

🔗
Bajo Acoplamiento

Módulos independientes que interactúan mediante contratos formales.

🧪
Testabilidad

Aislamiento total para inyectar mocks o stubs en pruebas unitarias con JUnit 5.

🛒 2. Nuestro Proyecto de Ejemplo: Tienda Virtual

Caso de Estudio Unificado

Para no estudiar cada principio con ejemplos aislados o desconectados, construiremos progresivamente el núcleo transaccional de una Tienda Virtual en Spring Boot que debe:

📦 1. Registrar Productos (catálogo de inventario).
🛒 2. Crear Pedidos (asociar cliente y líneas de compra).
🧮 3. Calcular el Total (aplicar sumas y reglas impositivas).
💳 4. Procesar Pagos (múltiples pasarelas y medios).
📧 5. Enviar Notificaciones (confirmaciones multicanal).
📁 Estructura Empresarial de Paquetes en Spring Boot
src/main/java/com/tienda/
│
├── controller/
│   └── PedidoController.java       // Endpoints REST (@RestController)
│
├── service/
│   ├── PedidoService.java          // Orquestación y casos de uso (@Service)
│   ├── FacturaService.java         // Lógica fiscal y cálculo de facturas
│   └── PagoService.java            // Gestión de pagos polimórficos
│
├── repository/
│   └── PedidoRepository.java       // Capa de persistencia (Spring Data JPA)
│
├── entity/
│   ├── Pedido.java                 // Entidad JPA mapeada a PostgreSQL
│   └── Producto.java               // Entidad JPA del ítem
│
└── dto/
    ├── PedidoRequest.java          // DTO inmutable con Java Records
    └── PedidoResponse.java         // DTO de salida para clientes API
S

Single Responsibility Principle (SRP)

"Una clase debe tener una única razón para cambiar." — Robert C. Martin

Esto no significa que una clase deba tener únicamente un método. Significa que debe responsabilizarse de un único actor de negocio o subsistema tecnológico bien delimitado.

❌ Paso 1: Identificar el Problema (Anti-patrón God Class / Servicio Monolítico) Código Incorrecto
PedidoService.java (Versión Violatoria de SRP) 
@Service
public class PedidoService {

    @Autowired
    private PedidoRepository repository;

    public void crearPedido(Pedido pedido) {
        // 1. Persistencia: Guardar pedido en base de datos PostgreSQL
        repository.save(pedido);

        // 2. Lógica matemática de negocio: Calcular total sumando ítems
        double total = pedido.getProductos()
                .stream()
                .mapToDouble(p -> p.getPrecio())
                .sum();

        // 3. Generación y formateo de factura fiscal
        System.out.println("Generando factura: " + total);

        // 4. Notificaciones: Envío de correo electrónico
        System.out.println("Enviando correo al cliente");
    }
}
⚠️ ¿Qué graves problemas de arquitectura tenemos aquí?
  • Múltiples razones para cambiar: Si mañana el área de contabilidad cambia el formato o los impuestos de la factura, se debe modificar PedidoService.
  • Si el equipo de infraestructura migra de SMTP a SendGrid o AWS SES para enviar correos, se debe modificar PedidoService.
  • Si cambian las reglas de descuentos sobre los productos, nuevamente se modifica la misma clase.
  • Imposible de testear en aislamiento: Probar la lógica de guardado arrastra necesariamente la emisión de facturas y los correos.
✅ Paso 2: Aplicar la Solución (Separación Estricta de Responsabilidades) Diseño Refactorizado
1. PedidoService.java (Solo coordina el caso de uso de creación) 
@Service
@RequiredArgsConstructor // Lombok: Genera constructor para inyección inmutable
public class PedidoService {

    private final PedidoRepository repository;
    private final FacturaService facturaService;
    private final EmailService emailService;

    public void crearPedido(Pedido pedido) {
        Pedido guardado = repository.save(pedido);
        facturaService.generar(guardado);
        emailService.enviarConfirmacion(guardado);
    }
}
2. FacturaService.java (Responsabilidad exclusiva: Facturación) 
@Service
public class FacturaService {

    public void generar(Pedido pedido) {
        double total = pedido.getProductos()
                .stream()
                .mapToDouble(Producto::getPrecio)
                .sum();
        System.out.println("Factura generada con total: $" + total);
    }
}
3. EmailService.java (Responsabilidad exclusiva: Enviar correos) 
@Service
public class EmailService {

    public void enviarConfirmacion(Pedido pedido) {
        System.out.println("Correo enviado al cliente para pedido ID: " + pedido.getId());
    }
}
🔍
¿Cómo diagnosticar una violación de SRP en tu código?

Pregúntate: "¿Esta clase tiene diferentes motivos de negocio independientes por los que tendría que ser modificada?" Si respondes afirmativamente, divide las responsabilidades en servicios especializados coordinados mediante composición.

O

Open/Closed Principle (OCP)

"Las entidades de software deben estar abiertas para su extensión, pero cerradas para su modificación." — Bertrand Meyer

Debemos ser capaces de añadir nuevo comportamiento al sistema sin tocar ni alterar las líneas de código que ya están probadas y operando en producción.

❌ Paso 1: Identificar el Problema (Cadenas frágiles de if / else / switch) Código Incorrecto
PagoService.java (Violación de OCP mediante cadenas de if-else) 
@Service
public class PagoService {

    public void procesarPago(String tipo, double monto) {
        if (tipo.equals("TARJETA")) {
            System.out.println("Procesando pago con tarjeta: " + monto);
        } else if (tipo.equals("PAYPAL")) {
            System.out.println("Procesando pago con PayPal: " + monto);
        } else if (tipo.equals("TRANSFERENCIA")) {
            System.out.println("Procesando transferencia bancaria: " + monto);
        }
    }
}
⚠️ ¿Qué sucede cuando el negocio solicita aceptar pagos con Criptomonedas o Apple Pay?
  • Estamos obligados a abrir PagoService.java y añadir otro bloque else if.
  • Existe alto riesgo de romper por error el flujo de tarjeta o PayPal que ya estaba funcionando.
  • El archivo crece indefinidamente violando la modularidad y dificultando el control de versiones.
✅ Paso 2: Aplicar la Solución (Contrato Polimórfico y Auto-registro en Spring) Diseño Refactorizado
1. Pago.java (Contrato abstracto) 
public interface Pago {
    void procesar(double monto);
}
2. Implementaciones Concretas Registradas como Beans de Spring 
@Service
public class PagoTarjeta implements Pago {
    @Override
    public void procesar(double monto) {
        System.out.println("Pago con tarjeta: $" + monto);
    }
}

@Service
public class PagoPayPal implements Pago {
    @Override
    public void procesar(double monto) {
        System.out.println("Pago con PayPal: $" + monto);
    }
}

@Service
public class PagoTransferencia implements Pago {
    @Override
    public void procesar(double monto) {
        System.out.println("Transferencia bancaria: $" + monto);
    }
}
3. PagoService.java (Inyecta automáticamente List<Pago> sin ifs) 
@Service
@RequiredArgsConstructor
public class PagoService {

    // Spring inyecta automáticamente TODOS los beans que implementan Pago
    private final List<Pago> metodosPago;

    public void procesarPago(String tipo, double monto) {
        Pago metodo = metodosPago.stream()
                .filter(p -> p.getClass().getSimpleName().equalsIgnoreCase(tipo))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException("Método de pago no soportado: " + tipo));

        metodo.procesar(monto);
    }
}
4. ¿El negocio pide pagos con Criptomonedas? ¡Solo creas una clase nueva! 
@Service
public class PagoCripto implements Pago {
    @Override
    public void procesar(double monto) {
        System.out.println("Procesando pago con criptomonedas (BTC/USDT): $" + monto);
    }
}
// ¡CERO modificaciones a PagoService, PagoTarjeta o PagoPayPal! Totalmente extensible.
🔍
¿Cómo diagnosticar una violación de OCP en tu código?

Pregúntate: "Si necesito agregar una nueva regla de negocio o variante, ¿tengo que modificar clases existentes que ya funcionan y están testeadas?" Si la respuesta es sí, reemplaza las sentencias condicionales por polimorfismo o el patrón Strategy.

L

Liskov Substitution Principle (LSP)

"Los objetos de una superclase deben poder ser reemplazados por objetos de sus subclases sin alterar el comportamiento correcto del programa." — Barbara Liskov (Turing Award)

Una subclase no solo debe compartir la sintaxis de los métodos del padre; debe respetar el contrato semántico y las expectativas de comportamiento sin lanzar excepciones inesperadas al ser invocada.

❌ Paso 1: Identificar el Problema (Herencia Rota con UnsupportedOperationException) Código Incorrecto
El clásico dilema: Aves que vuelan y pingüinos que lanzan excepciones 
// Clase Base
public class Ave {
    public void volar() {
        System.out.println("El ave está volando por los cielos");
    }
}

public class Aguila extends Ave {
    @Override
    public void volar() {
        System.out.println("El águila vuela a gran altura");
    }
}

public class Pinguino extends Ave {
    @Override
    public void volar() {
        // ¡VIOLACIÓN GRAVE DE LSP! Rompe el contrato de la clase padre
        throw new UnsupportedOperationException("Los pingüinos no pueden volar biológicamente");
    }
}
⚠️ ¿Qué catástrofe produce esto en tiempo de ejecución?
  • Si un cliente escribe: public void hacerVolar(Ave ave) { ave.volar(); } y le pasa una lista polimórfica de aves, la aplicación colapsará con un error en runtime cuando el turno sea del pingüino.
  • Obliga a ensuciar el código cliente con verificaciones feas tipo if (ave instanceof Pinguino).
  • La herencia no debe basarse en taxonomías de la vida real si el comportamiento esperado del software difiere.
✅ Paso 2: Aplicar la Solución (Segregación de Capacidades en Interfaces) Diseño Refactorizado
Jerarquía coherente basada en capacidades reales 
// Clase Base con lo común a TODAS las aves
public abstract class Ave {
    public abstract void comer();
}

// Capacidad aislada en interfaz
public interface Volador {
    void volar();
}

// El Águila come y vuela
public class Aguila extends Ave implements Volador {
    @Override
    public void comer() { System.out.println("El águila caza y come peces"); }

    @Override
    public void volar() { System.out.println("El águila planea alto"); }
}

// El Pingüino solo implementa Ave, ¡NO implementa Volador!
public class Pinguino extends Ave {
    @Override
    public void comer() { System.out.println("El pingüino come krill"); }
}

// Clientes desacoplados que NUNCA fallan por sustitución:
public void alimentar(Ave ave) { ave.comer(); } // Funciona para cualquier Ave
public void hacerVolar(Volador v) { v.volar(); } // Solo acepta entidades que garantizan vuelo
🔍
¿Cómo diagnosticar una violación de LSP en tu código?

Pregúntate: "Si sustituyo una referencia a la clase padre por cualquiera de sus clases hijas, ¿el programa mantiene su comportamiento correcto sin arrojar UnsupportedOperationException ni violar precondiciones?" Si una subclase deja métodos en blanco o arroja excepciones, revisa tu jerarquía de herencia.

I

Interface Segregation Principle (ISP)

"Ningún cliente debe ser forzado a depender de métodos que no utiliza." — Robert C. Martin

Es inmensamente preferible tener múltiples interfaces pequeñas, granulares y altamente cohesivas que una sola interfaz "gorda" cargada de responsabilidades dispares.

❌ Paso 1: Identificar el Problema (Interfaz "Gorda" / Fat Interface) Código Incorrecto
Dispositivo.java forzando operaciones no soportadas 
public interface Dispositivo {
    void imprimir();
    void escanear();
    void enviarFax();
}

public class ImpresoraBasica implements Dispositivo {
    @Override
    public void imprimir() {
        System.out.println("Imprimiendo documento físico...");
    }

    @Override
    public void escanear() {
        // ¡Esta impresora no tiene escáner óptico! Obligada a meter código basura
        throw new UnsupportedOperationException("Escaneo no disponible");
    }

    @Override
    public void enviarFax() {
        // ¡Tampoco tiene módem de fax!
        throw new UnsupportedOperationException("Fax no soportado");
    }
}
⚠️ Consecuencias de una Interfaz Demasiado Grande:
  • Métodos fantasmas o vacíos: Clases llenas de implementaciones que solo lanzan excepciones o no hacen nada.
  • Acoplamiento artificial: Si la firma de enviarFax() cambia para admitir número de país, la clase ImpresoraBasica se ve forzada a recompilarse y cambiar a pesar de ni siquiera tener fax.
✅ Paso 2: Aplicar la Solución (Interfaces Granulares y Específicas por Rol) Diseño Refactorizado
Interfaces modulares según capacidades individuales 
// Interfaces finas y cohesivas
public interface Imprimible {
    void imprimir();
}

public interface Escaneable {
    void escanear();
}

public interface Fax {
    void enviarFax();
}

// 1. Impresora básica: Solo implementa lo que verdaderamente hace
public class ImpresoraBasica implements Imprimible {
    @Override
    public void imprimir() {
        System.out.println("Imprimiendo en blanco y negro con tóner...");
    }
}

// 2. Impresora Multifuncional de Oficina: Combina múltiples interfaces con flexibilidad
public class ImpresoraMultifuncional implements Imprimible, Escaneable, Fax {
    @Override
    public void imprimir() { System.out.println("Imprimiendo a color dúplex..."); }
    @Override
    public void escanear() { System.out.println("Escaneando a PDF en alta resolución..."); }
    @Override
    public void enviarFax() { System.out.println("Transmitiendo fax digitalizado..."); }
}
🔍
¿Cómo diagnosticar una violación de ISP en tu código?

Pregúntate: "¿Estoy obligando a alguna clase a implementar métodos en blanco, lanzar UnsupportedOperationException o retornar null solo para complacer a una interfaz gigantesca?" Si es así, divide la interfaz en contratos más pequeños y específicos.

D

Dependency Inversion Principle (DIP)

"1. Los módulos de alto nivel no deben depender de módulos de bajo nivel; ambos deben depender de abstracciones.
2. Las abstracciones no deben depender de los detalles; los detalles deben depender de las abstracciones." — Robert C. Martin

Este principio es el corazón arquitectónico de Spring Boot. Es la base conceptual que permite a los contenedores de Inversión de Control (IoC) gestionar el ciclo de vida de los componentes.

❌ Paso 1: Identificar el Problema (Instanciación directa con operador `new`) Código Incorrecto
NotificacionService.java amarrado fuertemente a EmailService 
@Service
public class NotificacionService {

    // ¡VIOLACIÓN DIRECTA DE DIP! Instancia concreta con "new"
    private final EmailService emailService = new EmailService();

    public void notificar(String mensaje) {
        emailService.enviar(mensaje);
    }
}

public class EmailService {
    public void enviar(String mensaje) {
        System.out.println("Enviando correo: " + mensaje);
    }
}
⚠️ ¿Qué graves problemas introduce este diseño?
  • Acoplamiento concreto e irreversible: NotificacionService (módulo de alto nivel) depende directamente de la clase concreta EmailService (módulo de bajo nivel).
  • Si el negocio decide enviar notificaciones por WhatsApp, SMS o Push Notifications, estamos forzados a modificar el código interno de NotificacionService.
  • Pérdida de la potencia de Spring: Al instanciar con new, el objeto queda fuera del contenedor de Spring (sin proxies transaccionales, sin métricas, sin inyección de configuración @Value).
✅ Paso 2: Aplicar la Solución (Abstracción + Inyección de Dependencias por Constructor) Diseño Refactorizado
1. Notificador.java (La abstracción / contrato intermedio) 
public interface Notificador {
    void enviar(String mensaje);
}
2. Implementaciones Concretas con @Service y @Primary 
@Service
@Primary // Spring inyecta este bean por defecto ante ambigüedad
public class EmailService implements Notificador {
    @Override
    public void enviar(String mensaje) {
        System.out.println("Enviando correo electrónico corporativo: " + mensaje);
    }
}

@Service
public class WhatsAppService implements Notificador {
    @Override
    public void enviar(String mensaje) {
        System.out.println("Enviando mensaje por WhatsApp Business Cloud API: " + mensaje);
    }
}
3. NotificacionService.java (Solo conoce la abstracción Notificador) 
@Service
@RequiredArgsConstructor
public class NotificacionService {

    // Dependencia hacia la ABSTRACCIÓN (interfaz), NUNCA hacia la clase concreta
    private final Notificador notificador;

    public void notificar(String mensaje) {
        notificador.enviar(mensaje);
    }
}
🎯 Clarificación Crucial: DIP vs Inyección de Dependencias (DI)

DIP es un principio de diseño de software de alto nivel que postula depender de abstracciones. La Inyección de Dependencias (DI) es el patrón técnico / mecanismo de Spring Boot que inyecta la instancia concreta en tiempo de ejecución. Spring facilita aplicar DIP mediante DI, pero son conceptos complementarios.

🔍
¿Cómo diagnosticar una violación de DIP en tu código?

Pregúntate: "¿Mis servicios empresariales dependen directamente de clases concretas o crean objetos con 'new' cuando podrían depender de contratos e interfaces inyectadas por el contenedor de Spring?" Si es así, extrae la interfaz y delega la instanciación al framework.

📊 6. Resumen Comparativo de los Cinco Principios

Tabla de Síntesis

Utiliza esta tabla de referencia rápida para identificar y mitigar de inmediato los anti-patrones en cualquier pull request o proyecto:

Principio Problema que Evita Solución Arquitectónica Ejemplo en Nuestra Tienda
SRP Clases gigantescas ("God classes") que hacen demasiadas cosas a la vez. Separar responsabilidades en servicios con un único motivo de cambio. PedidoService solo coordina; la persistencia va a PedidoRepository y facturación a FacturaService.
OCP Modificar y quebrar código existente cada vez que se agrega una funcionalidad. Extender el comportamiento mediante polimorfismo e interfaces. Añadir PagoCripto creando una nueva clase que implementa Pago, sin tocar PagoService.
LSP Subclases que rompen el comportamiento o arrojan UnsupportedOperationException. Asegurar la sustitución correcta de clases respetando el contrato de la jerarquía. Separar la capacidad Volador de Ave; el pingüino es un ave que come, pero no implementa vuelo.
ISP Interfaces monolíticas ("fat interfaces") que obligan a implementar métodos innecesarios. Diseñar interfaces pequeñas, cohesivas y especializadas por rol. Dividir Dispositivo en Imprimible, Escaneable y Fax.
DIP Acoplamiento directo y rígido a clases concretas mediante el operador new. Depender de contratos/abstracciones e inyectar las dependencias. NotificacionService depende de Notificador; Spring inyecta EmailService o WhatsAppService.

🍃 7. ¿Cómo se Relaciona SOLID con el Ecosistema Spring Boot?

Framework & Patrones

Spring Boot ofrece herramientas integradas de primera clase diseñadas para facilitar el cumplimiento estricto de SOLID:

@Service / @Repository
Relacionado con: SRP

Organiza tu aplicación en capas limpias (Controlador REST, Lógica de Negocio y Persistencia Spring Data JPA), delimitando claramente los roles de cada componente.

Interfaces + List<T>
Relacionado con: OCP

Spring recolecta e inyecta automáticamente colecciones de beans que implementan la misma interfaz, permitiendo implementar Strategy sin modificar las clases clientes.

Polimorfismo & Herencia
Relacionado con: LSP

La sustitución pura de beans a nivel de contrato en el contenedor IoC garantiza que cualquier bean sustituto cumpla estrictamente con el contrato del tipo inyectado.

Interfaces Finas (@FunctionalInterface)
Relacionado con: ISP

Creación de interfaces específicas para servicios de solo lectura, escritores o transformadores funcionales que desacoplan los módulos clientes.

@RequiredArgsConstructor & @Primary
Relacionado con: DIP

Inyección limpia de dependencias por constructor inmutable, complementada con @Primary y @Qualifier para resolver abstracciones en tiempo de arranque.

⚠️ Atención crítica: Utilizar estas anotaciones de Spring no garantiza automáticamente que tu arquitectura sea SOLID. Las anotaciones son únicamente facilitadores tecnológicos; la calidad depende de tu análisis de responsabilidades y del diseño de las relaciones entre clases.

🚀 9. Mi Recomendación para Aprenderlos Realmente

Estrategia Profesional

No intentes implementar los cinco principios todos al mismo tiempo desde el día uno. Aprende primero a reconocer el síntoma o dolor en el código y después aplica la refactorización quirúrgica:

1. SRP
Refactorizar un servicio sobrecargado: Toma una clase de más de 300 líneas y extrae la persistencia, notificaciones y cálculos en servicios coordinados.
2. OCP
Eliminar cadenas if/else: Transforma un procesador de tipos o estados en una interfaz polimórfica inyectada por colección.
3. LSP
Sanear la jerarquía de herencia: Elimina las clases hijas que lanzan excepciones al llamar métodos del padre y migra a contratos por capacidades.
4. ISP
Segregar interfaces hinchadas: Divide contratos grandes en interfaces finas donde ningún cliente implemente métodos inútiles.
