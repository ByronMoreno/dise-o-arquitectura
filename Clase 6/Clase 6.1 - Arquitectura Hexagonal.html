Módulo Arquitectónico Avanzado

La Arquitectura Hexagonal
(Ports & Adapters)

Descubre cómo aislar de forma estricta la lógica de negocio de tus aplicaciones frente a frameworks, bases de datos y APIs externas. Domina la inversión de dependencias y el desacoplamiento tecnológico óptimo.

1. El Concepto y el Problema

Propuesta originalmente por Alistair Cockburn en 2005, la Arquitectura Hexagonal tiene como finalidad primordial aislar la lógica de negocio de las tecnologías externas. En otras palabras: el dominio del sistema no debe saber qué base de datos se utiliza, qué API REST expone los endpoints o bajo qué framework se ejecuta. Son las tecnologías las que deben adaptarse al negocio, y no a la inversa.

Arquitectura Tradicional

En un sistema en capas tradicional, las llamadas fluyen acopladas verticalmente hacia abajo. Cualquier cambio tecnológico impacta al negocio.

Usuario / Cliente
▼
Controlador (REST API)
▼
Servicio (Negocio / Spring)
▼
Repositorio (JPA / Hibernate)
▼
Base de Datos (PostgreSQL)

El Impacto del Acoplamiento

Si mañana decides migrar tu proyecto de:

  • ⚡ Framework: Spring Boot → Quarkus
  • 💾 Persistencia: PostgreSQL → MongoDB
  • 🌐 Transporte: REST API → GraphQL

En un diseño acoplado, te verás obligado a reescribir y recompilar las clases donde reside la lógica del negocio, puesto que importan dependencias directas del framework (ej. anotaciones de JPA, decoradores HTTP).

Problema Clave: La lógica de negocio termina secuestrada por las decisiones de infraestructura tecnológica.

2. Estructura Hexagonal

El hexágono no representa un límite de seis componentes, sino una abstracción visual. Simboliza que el dominio posee múltiples puertos simétricos para comunicarse con diversas tecnologías externas (bases de datos, colas de mensajería, consolas o navegadores).

⚠️ Regla de Oro: Las dependencias fluyen siempre al centro.

3. Los Tres Componentes Principales

El desacoplamiento del sistema se basa en tres componentes que dividen de manera estricta la lógica comercial del soporte tecnológico:

1

1. El Dominio (Negocio)

El núcleo del hexágono. Contiene las entidades de negocio y las reglas de validación (cálculo de comisiones, reglas de stock, etc.). Es código de lenguaje puro (Java, Python, C#) libre de imports de librerías como Spring Boot o JPA.

2

2. Los Puertos (Ports)

Interfaces Java. Representan los contratos de entrada y salida del negocio. Los puertos de entrada (API) definen lo que el sistema ofrece al exterior. Los puertos de salida (SPI) definen lo que el negocio requiere del exterior (ej. guardar un registro).

3

3. Los Adaptadores

Implementaciones tecnológicas de los puertos. Un adaptador de entrada traduce la petición externa (REST Controller, GraphQL) y llama a un caso de uso. Un adaptador de salida implementa un puerto (JPA Postgres, MongoDB Adapter) para interactuar con la infraestructura.

4. Regla de Dependencia

En arquitectura hexagonal, la regla más restrictiva e inviolable es la dirección del acoplamiento: Los adaptadores dependen de los puertos, y los puertos dependen del dominio.

Flujo de Dependencia Arquitectónica

Adaptadores

Controller, JPA Repository

➔
Puertos (Interfaces)

Casos de uso, Repositorios

➔
Dominio (Negocio)

Entidades de Lenguaje Puro

El dominio se sitúa en la cúspide de independencia. Bajo ninguna circunstancia una clase dentro del directorio domain puede realizar un import que apunte a clases de infrastructure o librerías externas del framework.

5. Comparación: Capas vs. Hexagonal

Elegir entre arquitectura tradicional en capas (N-Tier) y arquitectura hexagonal requiere comprender sus diferencias estructurales e impactos en el ciclo de vida del software:

Característica Arquitectura en Capas Arquitectura Hexagonal
Independencia del Framework Baja. El negocio suele depender de decoradores y herramientas de Spring/JPA. Total. El núcleo de negocio está escrito en código de lenguaje base sin dependencias.
Cambio de Base de Datos Complejo. La persistencia influye en el comportamiento de las capas superiores. Simple. Únicamente requiere desarrollar un nuevo adaptador de salida.
Flujo de Dependencias Hacia abajo (Presentación ➔ Negocio ➔ Datos). Hacia el centro (Adaptadores ➔ Puertos ➔ Dominio).
Facilidad de Pruebas Unitarias Dificultad media. Requiere inicializar mocks complejos del framework de persistencia. Extrema. Se testea el dominio instanciando mocks simples de las interfaces (puertos).
Curva de Aprendizaje Baja. Es el estándar clásico en la industria. Moderada. Requiere comprender inversión de dependencias y mapeo de objetos.

6. Práctica: Sistema de Biblioteca

Analicemos la estructura práctica de un caso de uso real: Prestar un Libro en un sistema de biblioteca. Al presionar cada pestaña, verás cómo se desacoplan las clases utilizando Java en un entorno Spring Boot.

domain/model/Libro.java - Objeto de dominio puro. Observa que no tiene anotaciones @Entity ni @Table de JPA. 

package domain.model;

public class Libro {
    private Long id;
    private String titulo;
    private boolean disponible;

    public Libro(Long id, String titulo, boolean disponible) {
        this.id = id;
        this.titulo = titulo;
        this.disponible = disponible;
    }

    public void prestar() {
        if (!this.disponible) {
            throw new IllegalStateException("El libro no está disponible");
        }
        this.disponible = false;
    }
    
    // getters y setters estándar...
}

application/usecases/PrestarLibroUseCase.java - Puerto de entrada y caso de uso que procesa la lógica de negocio. 

package application.usecases;

import domain.model.Libro;
import domain.repository.LibroRepository;

public class PrestarLibroUseCase {
    private final LibroRepository libroRepository;

    // Depende de la interfaz (Puerto de salida), no de PostgreSQL
    public PrestarLibroUseCase(LibroRepository libroRepository) {
        this.libroRepository = libroRepository;
    }

    public void ejecutar(Long libroId) {
        Libro libro = libroRepository.buscarPorId(libroId);
        libro.prestar(); // Lógica de negocio
        libroRepository.guardar(libro);
    }
}

domain/repository/LibroRepository.java - Puerto de salida (SPI). Es una interfaz que define lo que el dominio necesita para persistir datos. 

package domain.repository;

import domain.model.Libro;

public interface LibroRepository {
    Libro buscarPorId(Long id);
    void guardar(Libro libro);
}

infrastructure/rest/LibroController.java - Adaptador de entrada. Recibe peticiones HTTP, extrae parámetros y delega al caso de uso. 

package infrastructure.rest;

import application.usecases.PrestarLibroUseCase;
// Dependencia de Spring Boot (Solo permitida en la capa de infraestructura)
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/libros")
public class LibroController {
    private final PrestarLibroUseCase prestarLibroUseCase;

    public LibroController(PrestarLibroUseCase prestarLibroUseCase) {
        this.prestarLibroUseCase = prestarLibroUseCase;
    }

    @PostMapping("/{id}/prestamo")
    public ResponseEntity<Void> prestarLibro(@PathVariable Long id) {
        prestarLibroUseCase.ejecutar(id);
        return ResponseEntity.ok().build();
    }
}

infrastructure/persistence/LibroRepositoryPostgres.java - Adaptador de salida. Implementa el puerto de salida y usa JPA/Hibernate. 

package infrastructure.persistence;

import domain.model.Libro;
import domain.repository.LibroRepository;
import org.springframework.stereotype.Repository;

@Repository
public class LibroRepositoryPostgres implements LibroRepository {
    private final SpringDataLibroRepository jpaRepository;

    public LibroRepositoryPostgres(SpringDataLibroRepository jpaRepository) {
        this.jpaRepository = jpaRepository;
    }

    @Override
    public Libro buscarPorId(Long id) {
        LibroEntity entity = jpaRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("Libro no encontrado"));
        return new Libro(entity.getId(), entity.getTitulo(), entity.isDisponible());
    }

    @Override
    public void guardar(Libro libro) {
        LibroEntity entity = new LibroEntity(libro.getId(), libro.getTitulo(), libro.isDisponible());
        jpaRepository.save(entity);
    }
}
