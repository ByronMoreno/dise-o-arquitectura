1. Decisiones Arquitectónicas (ADRs)

Una Decisión de Arquitectura de Software (SAD) no es una elección casual. Es una postura de diseño que impacta significativamente en la estructura, comportamiento e infraestructura del software. Documentar estas elecciones mediante Architectural Decision Records (ADRs) evita la degradación del conocimiento técnico y previene la "deuda de diseño".

1

¿Por qué documentar?

Un ADR actúa como la bitácora del proyecto. Explica por qué se tomó una ruta tecnológica determinada y bajo qué restricciones históricas, evitando que futuros programadores reviertan decisiones justificadas.

2

Estructura del ADR

Un ADR típico contiene el Contexto (problema y restricciones), la Decisión (propuesta de diseño), el Estado (propuesto, aceptado, obsoleto) y las Consecuencias (impactos positivos y negativos).

3

Impacto en el Ciclo de Vida

Las decisiones tempranas son difíciles de cambiar. Conforme avanza el proyecto, el coste de modificar una decisión arquitectónica fundamental crece de manera exponencial en comparación con un cambio de lógica.

Ejemplo Práctico de un ADR Documentado:

ADR ID & Título ADR-004: Migración a API Gateway
Fecha 28 de Julio, 2026
Estado
Aceptado
Autor / Rol Arq. de Software Senior
Contexto del Problema
Nuestros clientes (Web y Móvil) consumen servicios directamente de 12 microservicios backend separados. Esto provoca un excesivo acoplamiento de URLs en el cliente, alta latencia debido a múltiples conexiones HTTPS consecutivas, problemas de gestión de CORS complejos, y la necesidad de implementar autenticación JWT en cada microservicio de manera redundante.
Decisión Tomada
Implementaremos un patrón API Gateway centralizado utilizando NestJS y Fastify. Todos los clientes consultarán únicamente el puerto del Gateway, el cual se encargará del enrutamiento de peticiones internas, la agregación de datos de múltiples microservicios en un único payload, el filtrado de seguridad SSL y la validación / extracción del token JWT en el borde del sistema.
Consecuencias Generadas
  • Positivo: Punto único de entrada. Se simplifica la seguridad (JWT) y el registro de llamadas (Logging). Los clientes no conocen la topología interna del backend.
  • Positivo: Reducción de latencia de red en clientes móviles mediante agregación de respuestas.
  • Negativo: Se introduce un Punto Único de Fallo (Single Point of Failure). Si el API Gateway cae, todo el sistema queda inaccesible.
  • Negativo: Costo adicional de latencia interna por puente (salto de red adicional de Gateway a microservicio).

2. Trade-offs Arquitectónicos

En arquitectura de software, no existen soluciones "perfectas", solo existen trade-offs (compromisos o equilibrios). Como afirman Ford y Richards en sus leyes de la arquitectura: "Si un arquitecto piensa que ha encontrado una solución que no tiene ningún aspecto negativo, es muy probable que no los haya identificado todavía".

Simulador de Trade-offs

Modifica los sliders de decisión arquitectónica para observar el impacto en los atributos clave del sistema.

Nivel de Cifrado y Seguridad Medio (SHA-256)
Aumentar la seguridad requiere algoritmos más complejos (ej. AES-256-GCM) y validación estricta de firmas en tránsito.
Nodos de Redundancia (Réplicas) 2 Nodos
Duplicar la cantidad de instancias del servidor mejora la disponibilidad pero requiere balanceadores y almacenamiento replicado.
Desacoplamiento (Servicios) Monolito Modular
Pasar de un monolito a microservicios distribuidos disminuye el acoplamiento pero introduce latencia de red interna.

3. Factores de Calidad (ISO 25010)

El estándar internacional ISO/IEC 25010 define un modelo estructurado para la evaluación de la calidad del producto de software. Describe los atributos de calidad sistémicos (no funcionales) indispensables para el éxito de una plataforma productiva.

Mantenibilidad (Facilidad de modularización y corrección) ★★★☆☆
Escalabilidad (Crecimiento ante volumen de carga) ★★☆☆☆
Portabilidad y Despliegue (Facilidad de instalación) ★★★★☆
Rendimiento y Latencia (Tiempos de respuesta iniciales) ★★★★★

Monolito Tradicional

Toda la lógica de negocio, persistencia e interfaz de usuario se compilan y despliegan en una única unidad de ejecución. Excelente para arranques rápidos y equipos pequeños, pero difícil de escalar individualmente.

Fortalezas (Pros)

  • Latencia de red interna nula.
  • Despliegue simple y unitario.
  • Pruebas de integración fáciles.

Debilidades (Cons)

  • Punto único de fallo total.
  • Escalado vertical obligatorio.
  • Largo tiempo de compilación global.

A continuación, compara cómo se codifica un mismo Endpoint REST GET (/api/productos) que retorna un listado en formato JSON, reflejando el enfoque sintáctico y arquitectónico de cada herramienta: 

@RestController
@RequestMapping("/api")
public class ProductController {

    private final ProductService productService;

    // Inyección de dependencias por constructor
    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping("/productos")
    public List<Product> getAllProducts() {
        return productService.findAll();
    }
}
from flask import Flask, jsonify
from services import ProductService

app = Flask(__name__)
product_service = ProductService() # Instanciación directa y manual

@app.route('/api/productos', methods=['GET'])
def get_all_products():
    products = product_service.find_all()
    return jsonify(products)

if __name__ == '__main__':
    app.run(port=5000)
from django.http import JsonResponse
from django.views import View
from .models import Product

# Django se basa en vistas de clase u orientadas a funciones mapeadas en urls.py
class ProductListView(View):
    def get(self, request):
        products = Product.objects.all().values('id', 'name', 'price')

import { Controller, Get } from '@nestjs/common';

5. Práctica: Angular, NestJS y más

Una de las mayores ventajas del ecosistema moderno de desarrollo de software es la simetría y coherencia arquitectónica entre el frontend (Angular) y el backend (NestJS). Ambos frameworks adoptan los principios de diseño de Angular originales: uso de TypeScript tipado de forma estricta, programación modular, fuerte inyección de dependencias (DI) nativa y desacoplamiento mediante decoradores.

Frontend

Angular (Estructura SPA)

Divide la interfaz de usuario en Componentes (HTML para vista, CSS para diseño, TypeScript para comportamiento), organizados en Módulos y comunicados con el backend mediante Servicios inyectables a través de peticiones HTTP.

Backend

NestJS (Arquitectura Limpia)

Estructura el servidor de forma idéntica: Controladores (mapean rutas HTTP y parámetros), Módulos (encapsulan lógica cohesiva) y Proveedores/Servicios (procesan lógica de bases de datos e integraciones).
