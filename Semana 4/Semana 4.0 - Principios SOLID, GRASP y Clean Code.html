UNIDAD 2: CALIDAD Y REFACTORIZACIÓN RDA7: MANTENIBILIDAD & SOLID

Principios SOLID, GRASP, Clean Code y Detección de Deuda Técnica

El código mal diseñado no colapsa inmediatamente: se degrada lentamente acumulando fricción, bugs colaterales y altos costos de mantenimiento. En esta semana profundizamos en los 5 principios SOLID de Robert C. Martin, los 9 patrones GRASP de asignación de responsabilidades de Craig Larman y el diagnóstico sistemático de Code Smells para transformar código frágil en software empresarial sostenible.

1 Los Cinco Principios SOLID

Pilares para crear software orientado a objetos tolerante al cambio

1. SRP: Single Responsibility Principle

"Una clase debe tener una sola razón para cambiar."

Violación común: La clase Factura calcula aranceles, se conecta a PostgreSQL para guardarse a sí misma y genera el HTML del comprobante.
Solución: Dividir en Factura (modelo de datos), FacturaRepository (persistencia) y FacturaPdfGenerator (renderizado).

2. OCP: Open/Closed Principle

"Las entidades de software deben estar abiertas para su extensión, pero cerradas para su modificación."

Violación común: Un bloque switch(tipoDescuento) que debe modificarse cada vez que la universidad crea un nuevo tipo de beca.
Solución: Declarar una interfaz EstrategiaDescuento e implementar clases concretas (BecaAcademica, DescuentoDeportivo).

3. LSP: Liskov Substitution Principle

"Los subtipos deben ser sustituibles por sus tipos base sin alterar la correctitud del programa." (Barbara Liskov)

Violación clásica: La clase Cuadrado hereda de Rectangulo, pero al invocar setAlto(10) modifica forzosamente el ancho, rompiendo los invariantes esperados por el cliente.

4. ISP: Interface Segregation Principle

"Los clientes no deben ser forzados a depender de interfaces con métodos que no utilizan."

Violación común: Una interfaz obesa (Fat Interface) Trabajador con métodos dictarClase(), cobrarMatricula() y mantenerServidores() obligando a clases a dejar métodos con throw new UnsupportedOperationException().

5. DIP: Dependency Inversion Principle

"Los módulos de alto nivel no deben depender de módulos de bajo nivel. Ambos deben depender de abstracciones. Las abstracciones no deben depender de los detalles; los detalles deben depender de las abstracciones."

Ejemplo Java: Inversión de Dependencias Correcta 
// 1. Abstracción (Puerto)
public interface NotificadorService {
    void enviarMensaje(String destinatario, String contenido);
}

// 2. Módulo de Bajo Nivel (Detalle / Adaptador)
@Service
public class SmtpEmailService implements NotificadorService {
    public void enviarMensaje(String destinatario, String contenido) {
        // Lógica de conexión SMTP con TLS...
    }
}

// 3. Módulo de Alto Nivel (Lógica de Negocio / Core)
@Service
public class MatriculaService {
    private final NotificadorService notificador; // Depende de la interfaz, NO de SmtpEmailService

    @Autowired // Inyección por constructor
    public MatriculaService(NotificadorService notificador) {
        this.notificador = notificador;
    }

    public void confirmarMatricula(Estudiante est) {
        // Reglas de negocio...
        notificador.enviarMensaje(est.getEmail(), "Tu matrícula ha sido confirmada.");
    }
}

2 Patrones GRASP (Craig Larman)

Guías fundamentales para asignar responsabilidades a clases y objetos

Patrón GRASP Problema que Resuelve Principio de Asignación de Responsabilidad
Experto en Información (Information Expert) ¿Cuál es el principio general para asignar responsabilidades a los objetos? Asignar la responsabilidad a la clase que posee la información necesaria para realizarla (ej. el total de una factura lo calcula Factura porque conoce sus líneas y aranceles).
Creador (Creator) ¿Quién debe ser responsable de instanciar un nuevo objeto? La clase A debe crear a B si A contiene, agrega fuertemente, registra o usa intensivamente a B (ej. Matricula crea DetalleMatricula).
Controlador (Controller) ¿Quién debe recibir y coordinar las peticiones del sistema que vienen de la UI? Un objeto que representa el caso de uso global (ej. MatriculaController), evitando que la UI se acople directamente a la base de datos o lógica profunda.
Bajo Acoplamiento (Low Coupling) ¿Cómo dar soporte a una baja dependencia y alta reutilización? Asignar responsabilidades de modo que la cantidad de clases asociadas sea mínima.
Alta Cohesión (High Cohesion) ¿Cómo mantener los objetos focalizados, comprensibles y manejables? Mantener clases pequeñas donde todos los métodos colaboren estrechamente en un mismo objetivo conceptual.

3 Filosofías Clean Code: KISS, DRY y YAGNI

Simplicidad pragmática y legibilidad del código

💋 KISS

Keep It Simple, Stupid: La mayoría de los sistemas funcionan mejor si se mantienen simples en lugar de complejos. Evitar la sobreingeniería y las jerarquías de herencia artificialmente profundas.

🌵 DRY

Don't Repeat Yourself: Toda pieza de conocimiento o lógica de negocio debe tener una representación única, inequívoca y autoritativa dentro del sistema. Evitar copiar y pegar bloques de código.

🚀 YAGNI

You Aren't Gonna Need It: No construyas funcionalidades basadas en especulaciones de "quizás lo usemos en el futuro". Construye solo lo que los requerimientos actuales exigen.

4 Taxonomía de Code Smells y Deuda Técnica

Identificando síntomas de descomposición del diseño

Categorías de Code Smells (Martin Fowler)

  • Bloaters (Hinchazones): Long Method (> 50 líneas), Large Class (> 500 líneas), Long Parameter List (> 4 parámetros), Primitive Obsession.
  • OO Abusers: Switch Statements repetidos (falta de polimorfismo), Refused Bequest (heredar pero lanzar excepción en métodos del padre).
  • Change Preventers: Divergent Change (una clase cambia por 3 razones distintas), Shotgun Surgery (un pequeño cambio requiere tocar 10 archivos).
  • Couplers (Acopladores): Feature Envy (un método usa más los datos de otra clase que los de la suya propia), Inappropriate Intimacy.

El Cuadrante de la Deuda Técnica (Fowler)

PrudenteTemeraria
Deliberada "Debemos salir a producción hoy; pagaremos la refactorización el próximo sprint." "No tenemos tiempo para hacer pruebas unitarias ni diseño formal; ¡saquen código ya!"
Inadvertida "Ahora que el sistema opera, entendemos cuál debió ser el diseño correcto." "¿Qué es la arquitectura en capas y por qué el SQL no debe ir en el frontend?"

5 Cuestionario de Principios SOLID y GRASP

Comprueba tu capacidad de detectar violaciones arquitectónicas

1. Si una clase concreta hereda de una clase base y al implementar un método lanza "UnsupportedOperationException", ¿qué principio SOLID se está violando directamente?
2. ¿Qué patrón GRASP recomienda asignar una responsabilidad a la clase que tiene la información necesaria para cumplirla?
3. Cuando un método de la clase A invoca continuamente múltiples getters de la clase B para realizar cálculos internos de B, ¿qué Code Smell se evidencia?
