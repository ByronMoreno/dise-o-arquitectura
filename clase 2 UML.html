Calidad del Software y Modelado UML

Aprende a formular y medir los pilares de la calidad de software no funcional (Mantenibilidad, Escalabilidad, Disponibilidad y Rendimiento) y a representarlos gráficamente a través de diagramas estructurales y dinámicos usando UML (Unified Modeling Language).

Objetivos de la Clase

Al finalizar esta sesión de aprendizaje, serás capaz de evaluar la calidad arquitectónica y modelar la estructura y comportamiento de sistemas de software con solidez:

Evaluar la Calidad

Identificar y formular métricas clave y tácticas de diseño para garantizar Mantenibilidad, Escalabilidad, Disponibilidad y Rendimiento.

Modelar Estructuras

Diseñar Diagramas de Clases, relaciones UML de dependencia, agregación y composición, y empaquetar de forma lógica.

Modelar Comportamiento

1. Calidad del Software (Atributos no Funcionales)

La calidad del software no se reduce a que el sistema cumpla con sus requerimientos funcionales directos. De acuerdo a la norma ISO/IEC 25010, las características no funcionales o arquitectónicas definen cómo se comporta el sistema bajo condiciones operativas reales:

Mantenibilidad

La facilidad con la que un sistema de software puede ser modificado para corregir fallos, mejorar su rendimiento o adaptarlo a un entorno cambiado. Un sistema mantenible tiene alta cohesión y bajo acoplamiento.

Escalabilidad

La capacidad del sistema de manejar una cantidad creciente de trabajo (ej. más peticiones por segundo o más usuarios concurrentes) añadiendo recursos de hardware de forma lineal.

Disponibilidad

El grado en el que un sistema se encuentra en un estado para realizar su función requerida en un momento dado. Se mide en porcentaje de tiempo activo (ej. SLA de 'cinco nueves': 99.999% de uptime).

Rendimiento

Relacionado con los tiempos de respuesta (latencia) y la cantidad de transacciones que el sistema puede procesar por unidad de tiempo (throughput) bajo cargas normales o pico.

2. Introducción a UML

El Lenguaje Unificado de Modelado (UML) es un estándar visual para especificar, visualizar, construir y documentar los artefactos de un sistema de software. UML proporciona una forma común de representar los planos del sistema, facilitando la comunicación entre arquitectos, desarrolladores y stakeholders.

Diagramas Estructurales

Representan la organización estática del sistema. Describen qué elementos componen el sistema (clases, interfaces, objetos, componentes) y cómo se relacionan físicamente. Ejemplos: Diagramas de Clases, Componentes y Despliegue.

Diagramas de Comportamiento

Representan el aspecto dinámico del sistema. Describen cómo se comporta el software en respuesta a eventos del tiempo y la interacción de los componentes entre sí. Ejemplos: Diagramas de Casos de Uso y Secuencia.

3. Diagramas Estructurales UML

Los diagramas estructurales definen los bloques lógicos y físicos de la arquitectura del software. Explora las pestañas a continuación para visualizar diagramas estructurales clave y comprender sus relaciones y empaquetamiento:

Diagrama de Clases Interactivo (Haz clic en clases o líneas de relación para ver explicaciones)

Haz clic en cualquiera de las clases o en las líneas de relación (como la flecha de generalización o el rombo de agregación) para examinar su semántica y reglas de modelado.

Asociación Simple

Conexión estructural básica entre clases. Indica una relación de conocimiento bidireccional o unidireccional (ej. Profesor dicta Curso).

Agregación

Relación débil de "Todo-Parte" (rombo vacío). Las partes pueden existir independientemente del todo (ej. un Estudiante existe sin pertenecer al Curso).

Composición

Relación fuerte de "Todo-Parte" (rombo relleno). Las partes mueren o se eliminan si el todo se destruye (ej. el Aula se destruye, el Edificio también).

Diagrama de Despliegue y Distribución Física

Diagrama de Despliegue: Muestra la topología de hardware e infraestructura sobre la cual se ejecutará la aplicación de software. Las cajas de tipo "cubo" representan nodos de procesamiento físicos o virtuales (nodos) interconectados por vías de comunicación (ej. HTTPS, TCP/IP, JDBC).

4. Diagramas de Comportamiento UML

Los diagramas de comportamiento modelan los aspectos dinámicos de los sistemas. Representan los flujos de control, los escenarios funcionales y la interacción de componentes a través del tiempo.

Casos de Uso

Mapea las fronteras funcionales del sistema. Describe los requerimientos funcionales a través de la interacción de los Actores (ej. Estudiante) y las operaciones del sistema (ej. Registrarse).

Secuencia

Muestra cómo interactúan múltiples objetos a nivel de llamadas de métodos y mensajes organizados de forma estrictamente cronológica de arriba hacia abajo.

5. Práctica: Sistema Académico

Esta sección práctica te guía en el modelado del Sistema de Gestión de Notas de UNIBE. El sistema debe permitir a los alumnos visualizar sus registros académicos y a los docentes cargar y modificar las notas finales de sus cursos.

El modelado de Casos de Uso separa las operaciones funcionales por Actor (roles de negocio). En nuestro portal académico:

Actor Caso de Uso Base Relaciones (<<include>> / <<extend>>)
Estudiante Consultar Calificaciones <<include>> Iniciar Sesión
Docente Cargar Notas Cursos <<include>> Iniciar Sesión / <<extend>> Modificar Nota (Opcional)
Administrador Habilitar Periodo Académico <<include>> Iniciar Sesión

A nivel de clases, la relación entre `Estudiante`, `Nota` e `Inscripción` se modela mediante herencias de clases y composiciones: 

// Mapeo del dominio Académico
public class Inscripcion {
    private Long id;
    private Estudiante estudiante;
    private Curso curso;
    
    // Composición: La nota no existe fuera del contexto de una Inscripción activa.
    private List<Nota> notasFinales;
}

public class Nota {
    private double valor;
    private String criterioEvaluacion; // ej. "Examen I", "Trabajo"
}
