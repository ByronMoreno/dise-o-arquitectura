1. Arquitectura de Software y Stakeholders

La Arquitectura de Software representa el conjunto de decisiones de diseño fundamentales acerca de la estructura y el comportamiento de un sistema. No consiste simplemente en escribir código; es la estructura organizacional global que determina cómo interactúan los componentes, cómo se distribuyen las responsabilidades y cómo se satisfacen los requerimientos no funcionales (atributos de calidad como escalabilidad, seguridad y mantenibilidad).

Definición formal (ISO/IEC/IEEE 42010):

"La arquitectura de un sistema es la organización fundamental de sus componentes, sus relaciones entre sí y con el entorno, y los principios que guían su diseño y evolución."

Los Stakeholders (Partes Interesadas)

Un sistema de software no se construye en el vacío. Existe un conjunto de personas u organizaciones que tienen un interés directo en el éxito, comportamiento o mantenimiento del software. El arquitecto de software debe balancear sus intereses conflictivos:

Usuarios Finales

Les interesa la usabilidad, rapidez del sistema, disponibilidad de las funciones y que el software resuelva sus necesidades cotidianas de forma fluida.

Clientes / Patrocinadores (Negocio)

Se enfocan en el costo de desarrollo, el tiempo de entrega (Time to Market), el retorno de inversión (ROI) y la viabilidad comercial a largo plazo.

Desarrolladores (Equipo Técnico)

Buscan una arquitectura clara, fácil de compilar, modularizada, bien documentada y que minimice el acoplamiento para poder programar sin pisarse el código.

Administradores de Operaciones (DevOps/SRE)

Priorizan la facilidad de despliegue, la observabilidad (logs y métricas), la tolerancia a fallos y la capacidad de escalar el sistema bajo demanda.

2. Puntos de Vista Arquitectónicos: Modelo 4+1 Vistas

Describir un sistema complejo desde una única perspectiva es imposible. Un desarrollador necesita ver diagramas de clases, mientras que un ingeniero de DevOps necesita ver servidores y redes. El estándar de facto para resolver esto es el Modelo de Vistas 4+1 propuesto por Philippe Kruchten.

3. Documentación Arquitectónica: Vistas Lógicas vs. Físicas

La documentación arquitectónica comunica las decisiones clave a los stakeholders. Sin documentación actualizada, los sistemas caen en la degradación arquitectónica (donde el código implementado se desvía drásticamente del diseño planeado). Dentro de los puntos de vista esenciales, destaca el contraste entre el mundo de las abstracciones lógicas y el mundo real de la infraestructura física.

Vista Lógica (Abstracción)

Responde a la pregunta: ¿Cómo se organiza conceptualmente el diseño del software?

Elementos de diseño: Clases, Interfaces, Interfaces de API, Capas de Negocio
UML relevante: Diagramas de Clases, Objetos, Interacción
Unidades lógicas: Módulos de Dominio (ej. Facturación, Inventario)
Independencia: Teóricamente independiente del hardware de ejecución
Mapeo

Vista Física (Infraestructura)

Responde a la pregunta: ¿Cómo y dónde se ejecuta concretamente el software?

Elementos reales: Servidores (VM), Contenedores Docker, Balanceadores, Redes
UML relevante: Diagramas de Despliegue (Deployment Diagrams)
Unidades físicas: Nodos de ejecución física y virtual
Configuración: IPs, Puertos, Cortafuegos (Firewalls), Latencias físicas

Estándares de Documentación: ISO 42010 y C4 Model

Actualmente, además del clásico modelo 4+1, existen estándares modernos para documentar la arquitectura de manera progresiva. El más popular en la industria ágil es el Modelo C4, el cual organiza la documentación como un mapa interactivo de zoom:

Nivel 1

Contexto

Muestra el sistema en el plano general: cómo interactúa con los usuarios humanos y con otros sistemas de software externos.

Nivel 2

Contenedores

Desglosa el sistema en sus aplicaciones web, móviles, bases de datos y microservicios ejecutables independientes.

Nivel 3

Componentes

Muestra las principales clases, interfaces o controladores internos que conforman cada uno de los contenedores.

Nivel 4

Código

Mapea las clases individuales, detalles de implementación del dominio y patrones de diseño orientados a objetos.

4. Estilos Arquitectónicos Tradicionales

Un Estilo Arquitectónico es un patrón recurrente de organización estructural para familias de sistemas de software. Define un vocabulario de componentes y conectores, junto con un conjunto de restricciones sobre cómo pueden combinarse. A continuación, explora los estilos tradicionales haciendo clic en las opciones del selector:

Arquitectura Monolítica

Unidad Única de Despliegue

En la arquitectura monolítica, todos los módulos funcionales del sistema (interfaz de usuario, lógica de negocio y acceso a datos) se compilan, empaquetan e implementan como una sola unidad de ejecución (un único archivo .war, .jar, o .exe). Comparten el ciclo de vida y la misma memoria en ejecución.

Ventajas (Pros)
  • Desarrollo inicial muy rápido y simple para prototipos.
  • Facilidad de pruebas unitarias e integradas locales.
  • Despliegue inicial trivial (copiar y ejecutar un solo archivo).
Desventajas (Cons)
  • Escalabilidad ineficiente (debes replicar todo el monolito).
  • Alto acoplamiento: un bug menor puede tumbar toda la aplicación.
  • Dificultad de actualización tecnológica por dependencia de stack único.

5. Arquitecturas Orientadas a Servicios: SOA vs. Microservicios

A medida que los sistemas empresariales crecieron, los monolitos se volvieron inmanejables. Surgió la necesidad de descentralizar y distribuir la computación en servicios reutilizables. Este camino evolutivo dio origen a dos filosofías: SOA (Service-Oriented Architecture) y los Microservicios.

SOA (Service-Oriented Architecture)

Estilo enfocado en integrar aplicaciones heterogéneas y sistemas heredados (legacy) en toda la empresa. Utiliza un Bus de Servicios Empresariales (ESB) centralizado que orquesta la comunicación usando protocolos complejos y pesados como SOAP, XML y WSDL.

Microservicios

Evolución nativa de la nube. Descompone el sistema en servicios de grano fino, autónomos, desplegables independientemente, que resuelven una única capacidad de negocio (Single Responsibility) y se comunican con protocolos ligeros (REST, gRPC, JSON).

Comparación Técnica Directa

Aunque ambos se basan en servicios, sus filosofías organizacionales e infraestructurales son drásticamente opuestas:

SOA (Arquitectura Orientada a Servicios)

Propósito clave: Interoperabilidad e integración corporativa
Comunicación central: ESB (Enterprise Service Bus) inteligente
Grano del servicio: Grano grueso (Coarse-grained)
Base de Datos: Base de datos compartida tradicional
Protocolos: SOAP, WSDL, XML (Pesados)
VS

Microservicios

Propósito clave: Despliegue rápido, agilidad y escalamiento
Comunicación central: Mensajería ligera (REST, gRPC, Kafka)
Grano del servicio: Grano fino (Fine-grained)
Base de Datos: Base de datos por servicio (Autónoma)
Protocolos: HTTP, JSON, gRPC, Protobuf (Ligeros)

Práctica: Comparación de Arquitecturas Reales (E-Commerce)

Para consolidar el aprendizaje, analizaremos un caso de estudio real: la evolución arquitectónica de una plataforma de comercio electrónico (E-Commerce) a medida que escala su base de usuarios. Veremos la transición técnica desde una arquitectura monolítica en capas hasta microservicios distribuidos.

En la fase inicial (Monolítica), todas las capacidades de negocio (Usuarios, Productos, Pedidos) residen en el mismo proyecto Java, organizadas jerárquicamente por capas de código (Controller, Service, Repository). La base de datos es única y compartida: 

// Estructura típica de paquetes en un Monolito en Capas (Single App)
package com.ecommerce.monolith;

// Todos los dominios conviven dentro del mismo espacio de memoria
import com.ecommerce.monolith.user.controller.UserController;
import com.ecommerce.monolith.product.controller.ProductController;
import com.ecommerce.monolith.order.controller.OrderController;

@SpringBootApplication
public class ECommerceApplication {
    public static void main(String[] args) {
        // Se levanta un único servidor web embebido (Tomcat) para toda la tienda
        SpringApplication.run(ECommerceApplication.class, args);
    }
}

/* 
  * Acoplamiento a nivel de Base de Datos:
  * Si la base de datos PostgreSQL compartida colapsa por una consulta pesada 
  * en el módulo de recomendaciones, todo el sistema de compras (Orders) deja de funcionar.
  */

Al migrar a microservicios, el sistema se divide en servicios desplegables por separado. Cada servicio corre en su propio contenedor (Docker) y gestiona de forma autónoma su propio almacenamiento de datos persistentes: 

version: "3.8"
services:
  api-gateway:
    image: ecommerce/api-gateway:latest
    ports:
      - "8080:8080" # Punto de entrada unificado para clientes web/móvil

  user-service:
    image: ecommerce/user-service:latest
    environment:
      - DB_URL=jdbc:postgresql://user-db:5432/users

  catalog-service:
    image: ecommerce/catalog-service:latest
    environment:
      - DB_URL=mongodb://catalog-db:27017/products # MongoDb ideal para catálogo flexible

  order-service:
    image: ecommerce/order-service:latest
    environment:
      - DB_URL=jdbc:postgresql://order-db:5432/orders

Resumen comparativo de atributos de calidad evaluados en el rediseño arquitectónico del E-Commerce:

Atributo de Calidad Monolito en Capas Microservicios Distribuidos
Despliegue Sencillo (Un solo bloque / archivo) Complejo (Múltiples contenedores, Kubernetes)
Escalabilidad En bloque (Ineficiente en consumo) Granular e independiente por servicio
Tolerancia a fallos Baja (Fallo en un módulo afecta todo) Alta (Aislamiento de fallos en cascada)
Consistencia de Datos Inmediata (Transacciones ACID en BD única) Eventual (Sincronización por eventos / Kafka)
