Código Java y Estructuras de Carpetas

Aterriza los conceptos teóricos de la clase. Analiza a profundidad cómo se organizan físicamente los directorios de archivos (árboles de proyecto) y cómo se implementa el código fuente Java en la práctica para la arquitectura monolítica, cliente-servidor y en capas.

1. Arquitectura Monolítica

En un monolito, **todo el sistema vive dentro del mismo proyecto y proceso**. Se compila y empaqueta en un único artefacto (como un archivo .jar o .war). Los componentes internos interactúan llamándose directamente en memoria mediante código Java ordinario (llamadas a métodos en la pila de ejecución local), compartiendo la base de datos física.

Árbol de Directorios del Proyecto

  • 📂 tienda-monolito // Raíz del proyecto Maven
    • 📄 pom.xml // Archivo de dependencias único
    • 📂 src
      • 📂 main
        • 📂 java
          • 📂 com
            • 📂 tienda
              • 📄 MonolithicApplication.java // Clase de entrada única
              • 📂 usuarios // Módulo de Usuarios (todo en el mismo directorio)
                • 📄 UserController.java
                • 📄 UserService.java
                • 📄 User.java
              • 📂 pedidos // Módulo de Pedidos (en el mismo espacio de compilación)
                • 📄 OrderController.java
                • 📄 OrderService.java // Llama a UserService directamente en RAM
                • 📄 Order.java
        • 📂 resources
          • 📄 application.properties // Configuración global

Código Java: Comunicación Interna Directa

Al estar en el mismo proceso, un servicio puede inyectar y llamar directamente a otro mediante simples referencias a objetos. No existe la latencia de red. 

package com.tienda;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

// Levanta toda la infraestructura, controladores de usuarios y pedidos en un solo proceso JVM
@SpringBootApplication
public class MonolithicApplication {
    public static void main(String[] args) {
        SpringApplication.run(MonolithicApplication.class, args);
    }
}
package com.tienda.pedidos;

import com.tienda.usuarios.UserService; // Importación de clase directa local
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final UserService userService; // Inyección directa de dependencia en memoria

    public OrderService(UserService userService) {
        this.userService = userService;
    }

    public Order crearPedido(Long usuarioId, Double monto) {
        // Llamamos al método directamente en la RAM. Rápido y sin red.
        if (!userService.existeUsuario(usuarioId)) {
            throw new IllegalArgumentException("El usuario no existe");
        }
        return new Order(usuarioId, monto, "CREADO");
    }
}

2. Estilo Cliente-Servidor

En este estilo, el sistema se divide en **dos proyectos o módulos físicos independientes**: uno que aloja la interfaz de usuario o solicita datos (Cliente) y otro que expone recursos y procesa peticiones de negocio (Servidor). El cliente se comunica con el servidor a través de un protocolo de red (por ejemplo, HTTP haciendo llamadas REST).

Árbol de Directorios del Proyecto

  • 📂 tienda-cliente-servidor // Carpeta raíz contenedora
    • 📂 servidor-api // PROYECTO 1: Backend que expone REST
      • 📄 pom.xml
      • 📂 src/main/java/com/tienda/server
        • 📄 ServerApp.java
        • 📄 ProductApiController.java // Expone datos en formato JSON
    • 📂 cliente-desktop // PROYECTO 2: Interfaz Swing que corre en la PC del usuario
      • 📄 pom.xml
      • 📂 src/main/java/com/tienda/client
        • 📄 ClientApp.java
        • 📄 ProductListFrame.java // Interfaz gráfica UI
        • 📄 HttpApiService.java // Realiza las peticiones de red al Servidor

Código Java: Interacción a través de Red

Observa cómo el Servidor expone un puerto local (ej. 8080) con formato JSON, y el Cliente utiliza el protocolo HTTP para solicitar y parsear remotamente la información de los productos. 

package com.tienda.server;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;
import java.util.List;

@RestController
public class ProductApiController {

    // El servidor expone el recurso a través de un endpoint HTTP público
    @GetMapping("/api/productos")
    public List<String> obtenerProductos() {
        // Devuelve la lista en texto. Spring Boot la serializa automáticamente a JSON.
        return List.of("Laptop Dell", "Mouse Inalámbrico", "Teclado Mecánico");
    }
}
package com.tienda.client;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class HttpApiService {
    private final HttpClient httpClient;

    public HttpApiService() {
        this.httpClient = HttpClient.newHttpClient();
    }

    public String obtenerProductosDelServidor() throws Exception {
        // El cliente configura la URL del nodo físico del servidor
        HttpRequest request = HttpRequest.newBuilder()
                .uri(new URI("http://localhost:8080/api/productos"))
                .GET()
                .build();

        // Realiza la petición de red bloqueante (I/O)
        HttpResponse<String> response = httpClient.send(request, HttpResponse.BodyHandlers.ofString());
        
        // Retorna el JSON crudo del catálogo recibido
        return response.body();
    }
}

3. Arquitectura en Capas (Layered)

En la arquitectura en capas, el código de la aplicación se divide horizontalmente por **responsabilidades técnicas**. Cada capa tiene un rol específico y se comunica únicamente con la capa inmediatamente inferior para asegurar el desacoplamiento. Las tres capas clásicas de diseño son: **Presentación (UI/Controller)**, **Dominio/Negocio (Service)** e **Infraestructura (Repository/DAO)**.

Árbol de Directorios del Proyecto

A diferencia del monolito clásico por dominios, las carpetas se dividen explícitamente por el rol técnico de la capa en la que residen:

  • 📂 tienda-arquitectura-capas
    • 📄 pom.xml
    • 📂 src/main/java/com/tienda/layered
      • 📄 LayeredApplication.java
      • 📂 controller // CAPA 1: Presentación / Controlador de APIs
        • 📄 ProductController.java
      • 📂 service // CAPA 2: Lógica de negocio (Reglas comerciales)
        • 📄 ProductService.java
      • 📂 repository // CAPA 3: Acceso a datos (SQL/Bases de datos)
        • 📄 ProductRepository.java
        • 📄 ProductRepositoryImpl.java
      • 📂 model // Entidades compartidas por las capas
        • 📄 Product.class

Código Java: Flujo de Arriba hacia Abajo

Compara las tres clases correspondientes. La petición fluye estrictamente en un sentido descendente: **Controller ➔ Service ➔ Repository**. 

package com.tienda.layered.controller;

import com.tienda.layered.model.Product;
import com.tienda.layered.service.ProductService; // Conecta con la capa inferior
import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/productos")
public class ProductController {
    private final ProductService productService;

    // Se inyecta la capa de negocio inmediatamente inferior
    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping
    public List<Product> listar() {
        return productService.obtenerCatalogoConDescuento();
    }
}
package com.tienda.layered.service;

import com.tienda.layered.model.Product;
import com.tienda.layered.repository.ProductRepository; // Conecta con la capa inferior
import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class ProductService {
    private final ProductRepository productRepository;

    // Inyecta el repositorio de acceso a infraestructura
    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    public List<Product> obtenerCatalogoConDescuento() {
        List<Product> lista = productRepository.findAll();
        // Regla de negocio: Aplicar un 10% de descuento corporativo
        lista.forEach(p -> p.setPrecio(p.getPrecio() * 0.9));
        return lista;
    }
}
package com.tienda.layered.repository;

import com.tienda.layered.model.Product;
import java.util.List;

// Interfaz que abstrae la base de datos (desacopla el motor físico de base de datos)
public interface ProductRepository {
    List<Product> findAll();
}

/*
  * Nota de diseño: La implementación física de esta interfaz (ProductRepositoryImpl)
  * será la encargada de abrir la conexión SQL mediante JDBC o JPA. La capa de Service
  * nunca sabrá si estamos usando Postgres, Oracle o una lista simulada en memoria.
  */

4. Otros Estilos Arquitectónicos Tradicionales

Existen otros estilos arquitectónicos tradicionales que resuelven problemas específicos de procesamiento, extensibilidad y coordinación de conocimiento distribuidos en el desarrollo de software.

4.1 Filtros y Tuberías (Pipes and Filters)

El flujo de datos se procesa secuencialmente a través de componentes independientes (**filtros**) conectados por canales de comunicación (**tuberías**). Muy común en procesamiento de datos (ej. pipelines de datos, transformaciones de texto, compiladores y comandos de consola).

Árbol de Directorios

  • 📂 tienda-pipes-filters
    • 📄 pom.xml
    • 📂 src/main/java/com/tienda/pipeline
      • 📄 PipelineApp.java // Orquestador y ejecución del flujo
      • 📄 Filter.java // Interfaz genérica del Filtro
      • 📄 TextCleaningFilter.java // Filtro 1: Remueve caracteres extraños
      • 📄 EncryptingFilter.java // Filtro 2: Encripta la cadena final

Código Java

package com.tienda.pipeline;

import java.util.ArrayList;
import java.util.List;

// Contrato para los filtros individuales
interface Filter<T> {
    T execute(T input);
}

// Orquestador (Pipeline / Tubería) que encadena la ejecución
public class PipelineApp {
    private final List<Filter<String>> filters = new ArrayList<>();

    public void registerFilter(Filter<String> filter) {
        filters.add(filter);
    }

    public String process(String input) {
        String temp = input;
        for (Filter<String> filter : filters) {
            temp = filter.execute(temp); // El output del filtro actual es el input del siguiente
        }
        return temp;
    }

    public static void main(String[] args) {
        PipelineApp pipeline = new PipelineApp();
        pipeline.registerFilter(new TextCleaningFilter());
        pipeline.registerFilter(new EncryptingFilter());

        String resultado = pipeline.process("¡Hola @Mundo!");
        System.out.println(resultado);
    }
}
package com.tienda.pipeline;

// Filtro 1: Remueve caracteres no alfanuméricos
class TextCleaningFilter implements Filter<String> {
    @Override
    public String execute(String input) {
        return input.replaceAll("[^a-zA-Z0-9 ]", "");
    }
}

// Filtro 2: Encriptación básica César
class EncryptingFilter implements Filter<String> {
    @Override
    public String execute(String input) {
        StringBuilder sb = new StringBuilder();
        for (char c : input.toCharArray()) {
            sb.append((char) (c + 1)); // Desplazamiento simple
        }
        return sb.toString();
    }
}

4.2 Microkernel (Arquitectura de Plug-ins)

Consiste en un sistema núcleo básico (**kernel**) que expone las operaciones mínimas esenciales de ejecución y permite extender su funcionalidad agregando módulos independientes (**plug-ins**) sin modificar la base central. Ejemplos muy comunes son navegadores web, IDEs (VS Code) y reproductores multimedia.

Árbol de Directorios

  • 📂 tienda-microkernel
    • 📄 pom.xml
    • 📂 src/main/java/com/tienda/microkernel
      • 📂 core // Núcleo del sistema
        • 📄 KernelApp.java
        • 📄 PaymentPlugin.java // Contrato base para plugins
      • 📂 plugins // Extensiones modulares independientes
        • 📄 PaypalPlugin.java
        • 📄 StripePlugin.java

Código Java

package com.tienda.microkernel.core;

import java.util.HashMap;
import java.util.Map;

// Interfaz de Plugin que define el contrato de extensión
interface PaymentPlugin {
    void processPayment(double amount);
    String getPluginName();
}

// Microkernel básico que registra y ejecuta las extensiones sin saber qué hacen
public class KernelApp {
    private final Map<String, PaymentPlugin> registry = new HashMap<>();

    public void registerPlugin(PaymentPlugin plugin) {
        registry.put(plugin.getPluginName(), plugin);
    }

    public void executePayment(String provider, double amount) {
        PaymentPlugin plugin = registry.get(provider);
        if (plugin == null) {
            System.out.println("Error: Plugin no soportado.");
        } else {
            plugin.processPayment(amount); // Ejecución delegada al módulo
        }
    }
}
package com.tienda.microkernel.plugins;

import com.tienda.microkernel.core.PaymentPlugin;

// Plugin de PayPal implementado fuera del Core
public class PaypalPlugin implements PaymentPlugin {
    @Override
    public void processPayment(double amount) {
        System.out.println("Procesando $" + amount + " a través del API de PayPal");
    }

    @Override
    public String getPluginName() {
        return "PAYPAL";
    }
}

// Plugin de Stripe implementado fuera del Core
public class StripePlugin implements PaymentPlugin {
    @Override
    public void processPayment(double amount) {
        System.out.println("Procesando $" + amount + " a través del SDK de Stripe");
    }

    @Override
    public String getPluginName() {
        return "STRIPE";
    }
}

4.3 Pizarra (Blackboard)

Múltiples subsistemas independientes (**expertos o fuentes de conocimiento**) cooperan compartiendo una base de datos centralizada común (**la pizarra**) para resolver problemas complejos de IA tradicional o reconocimiento de patrones, donde ninguna regla lógica predefinida por sí sola puede dar la solución absoluta.

Árbol de Directorios

  • 📂 tienda-blackboard
    • 📂 src/main/java/com/tienda/blackboard
      • 📄 Blackboard.java // Almacén central de conocimiento
      • 📄 Controller.java // Coordina las llamadas a los expertos
      • 📄 KnowledgeSource.java // Contrato base para los expertos
      • 📄 TaxExpert.java // Experto 1: Calcula el IVA de la compra
      • 📄 DiscountExpert.java // Experto 2: Aplica descuentos por festividades

Código Java

package com.tienda.blackboard;

import java.util.ArrayList;
import java.util.List;

// Pizarra: almacena el estado actual del cálculo
public class Blackboard {
    public double basePrice;
    public double taxAmount;
    public double discountAmount;
    public double totalPrice;
}

// Controlador: ejecuta a los expertos secuencialmente o en base a la pizarra
class Controller {
    private final List<KnowledgeSource> experts = new ArrayList<>();

    public void addExpert(KnowledgeSource expert) {
        experts.add(expert);
    }

    public void solve(Blackboard blackboard) {
        for (KnowledgeSource expert : experts) {
            expert.updateBlackboard(blackboard); // Los expertos leen y actualizan el estado compartido
        }
        blackboard.totalPrice = blackboard.basePrice + blackboard.taxAmount - blackboard.discountAmount;
    }
}
package com.tienda.blackboard;

// Interfaz para los expertos
interface KnowledgeSource {
    void updateBlackboard(Blackboard blackboard);
}

// Experto 1: Calcula impuesto (IVA 19%)
class TaxExpert implements KnowledgeSource {
    @Override
    public void updateBlackboard(Blackboard blackboard) {
        blackboard.taxAmount = blackboard.basePrice * 0.19;
    }
}

// Experto 2: Aplica un descuento fijo de $10 si la compra supera los $100
class DiscountExpert implements KnowledgeSource {
    @Override
    public void updateBlackboard(Blackboard blackboard) {
        if (blackboard.basePrice > 100) {
            blackboard.discountAmount = 10.0;
        }
    }
}
