UNIDAD 1 RDA2: DINÁMICA & C4 MODEL

Modelado Dinámico y Documentación Arquitectónica C4

Mientras que las clases muestran los ladrillos del edificio, los diagramas de interacción y el modelo C4 revelan cómo fluye la vida dentro del sistema. En esta semana aprendemos a modelar el intercambio de mensajes en el tiempo (Secuencia), el ciclo de vida de las entidades (Estados), y a crear mapas arquitectónicos comprensibles para humanos y máquinas mediante el modelo C4.

1 ¿Por Qué Necesitamos el Modelado Dinámico?

La dimensión temporal y el comportamiento reactivo del software

Un diagrama de clases nos dice que una Matrícula está asociada a un Estudiante y a una PasarelaPago, pero no nos dice: ¿Quién invoca a quién primero? ¿Qué ocurre si la pasarela responde con un Timeout de 5 segundos? ¿Cómo se asegura la consistencia de los datos?

El modelado dinámico responde a estas preguntas mediante dos perspectivas:
1. Interacción entre objetos: Diagramas de Secuencia.
2. Evolución interna de un objeto: Diagramas de Máquinas de Estados y Diagramas de Actividades.

2 Anatomía Rigurosa del Diagrama de Secuencia

Líneas de vida, tipología de mensajes y fragmentos combinados

Líneas de Vida y Focos de Activación

• Línea de Vida (Lifeline): Línea vertical punteada que representa la existencia de un participante a lo largo del tiempo.
• Foco de Activación (Execution Bar): Rectángulo estrecho superpuesto que indica que el objeto está ejecutando una operación activa.
• Destrucción: Marcada con una cruz (X) al final de la línea cuando el objeto es liberado o eliminado de la memoria.

Tipos de Mensajes en UML 2.5

• Síncrono (→►): Flecha sólida con punta triangular llena. El emisor se bloquea esperando la respuesta.
• Asíncrono (→): Flecha abierta continua. El emisor despacha el mensaje y continúa su ejecución sin esperar (ej. envío a Kafka o RabbitMQ).
• Respuesta / Retorno (‐‐>): Flecha discontinua abierta que devuelve el control o resultado al invocador.

Fragmentos Combinados (Control de Flujo)

Operador Significado Caso de Uso Típico
alt (Alternative) Estructura condicional excluyente (if / else / switch). Divide la secuencia con una línea punteada y guardas [condición]. Si saldo ≥ arancel: confirmar matrícula; de lo contrario: rechazar por fondos insuficientes.
opt (Optional) Bloque condicional sin rama falsa (if simple). Solo se ejecuta si la guarda es verdadera. Si el estudiante solicitó factura con RUC: invocar servicio de facturación electrónica SRI.
loop (Loop) Iteración repetitiva (for / while) con condición de parada. Por cada asignatura seleccionada en el carrito: verificar cupo y registrar el arancel.
par (Parallel) Ejecución concurrente o multitarea en hilos independientes. Despachar SMS de confirmación al estudiante y notificar simultáneamente al CRM de tesorería.

3 Diagramas de Máquinas de Estados y Actividades

Ciclo de vida de entidades y modelado de flujos paralelos con carriles

Diagrama de Estados (State Machine)

Modela todos los estados posibles por los que transita un objeto y los eventos que provocan el cambio.

Elementos clave:
• Estado: Condición o situación en la vida del objeto (ej. REGISTRADA, PAGADA, ANULADA).
• Transición: Evento [Guarda] / Acción
• Acciones Internas: entry / al ingresar, do / mientras permanece, exit / al salir.

Diagrama de Actividades y Swimlanes

Representa el flujo de trabajo operacional de un proceso de negocio complejo:

• Nodos de Decisión y Merge: Rombos que bifurcan o unifican flujos según condiciones.
• Fork y Join: Barras sólidas horizontales/verticales para iniciar o sincronizar ramas concurrentes.
• Carriles (Swimlanes): Columnas que delimitan qué actor o subsistema es responsable de cada actividad.

4 El Modelo C4 de Arquitectura (Simon Brown)

Mapas jerárquicos de arquitectura de software a diferentes escalas

Así como Google Maps permite hacer zoom desde el planeta Tierra hasta una calle específica, el Modelo C4 define 4 niveles de abstracción para comunicar la arquitectura sin ambigüedades:

Nivel 1: Diagrama de Contexto del Sistema

Audiencia: Directores, Product Owners, stakeholders y desarrolladores.
Objetivo: Muestra la imagen global: las Personas (usuarios) y los Sistemas Externos que interactúan con el sistema de software delimitado en el centro.
Omite: Protocolos detallados, lenguajes, frameworks o detalles de base de datos.

Nivel 2: Diagrama de Contenedores

Audiencia: Arquitectos, desarrolladores, ingenieros DevOps/SRE.
Objetivo: Muestra los bloques ejecutables/desplegables por separado (Single-Page App React, API Backend Spring Boot, Base de Datos PostgreSQL, Broker Kafka) y los protocolos de comunicación entre ellos (HTTPS/JSON, JDBC).
Nota: "Contenedor" en C4 no significa necesariamente Docker; significa cualquier unidad ejecutable.

Los otros dos niveles de C4:
• Nivel 3 (Componentes): Descompone un contenedor individual en sus componentes internos (Controladores, Servicios, Repositorios).
• Nivel 4 (Código): Detalle a nivel de clases UML (se recomienda generarlo automáticamente con IDEs).

5 Código PlantUML: Secuencia y C4 Context

Modelos interactivos listos para documentación técnica

secuencia_pago_matricula.puml 
@startuml
autonumber
skinparam responseMessageBelowArrow true
skinparam style strictuml

actor "Estudiante" as est
boundary "Portal Web (React)" as web
control "ServicioMatricula" as svc
entity "BD PostgreSQL" as bd
boundary "Pasarela Pago" as gateway

est -> web : Confirmar pago de matrícula
activate web

web -> svc : POST /api/v1/matriculas/{id}/pagar
activate svc

svc -> bd : Consultar arancel pendiente
activate bd
bd --> svc : Monto: $850.00 (Estado: PENDIENTE)
deactivate bd

svc -> gateway : Procesar cargo (TokenTarjeta, $850.00)
activate gateway

alt Transacción Aprobada por el Banco
    gateway --> svc : AuthCode: "TX-998822", Estado: APROBADO
    svc -> bd : UPDATE Matricula SET estado = 'PAGADA'
    svc --> web : 200 OK (Comprobante generado)
    web --> est : Pantalla de Matrícula Exitosa
else Fondos Insuficientes o Tarjeta Rechazada
    gateway --> svc : Error: "INSUFFICIENT_FUNDS"
    deactivate gateway
    svc --> web : 402 Payment Required (Motivo rechazo)
    web --> est : Alerta: "Transacción rechazada por el banco"
end

deactivate svc
deactivate web
@enduml
