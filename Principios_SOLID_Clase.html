Principios SOLID de Diseño de Software

Aprende el acrónimo acuñado por Robert C. Martin (Uncle Bob) que define los cinco principios fundamentales de la programación orientada a objetos para conseguir código mantenible, cohesivo, flexible y fácilmente testeable.

Objetivos de la Clase

SOLID no son reglas rígidas ni algoritmos, sino directrices de diseño arquitectónico. Al estudiar esta guía conseguirás:

Identificar Huelgas de Diseño

Reconocer violaciones a los principios SOLID en código base legado analizando síntomas como rigidez y fragilidad.

Desacoplar Componentes

Estructurar dependencias basándose en abstracciones en lugar de implementaciones concretas para modularizar el código.

Refactorizar Código

Aplicar técnicas de refactorización limpia y patrones de diseño utilizando ejemplos interactivos de "Antes y Después".

S: Single Responsibility Principle (Responsabilidad Única)

El principio de Responsabilidad Única establece que una clase debe tener una sola razón para cambiar. Esto significa que una clase debe resolver una única tarea o tener una sola responsabilidad dentro del sistema. 

// Esta clase tiene MULTIPLES razones para cambiar:
// 1. Gestión de datos del pedido
// 2. Lógica de formato de impresión / PDF
// 3. Lógica de persistencia en Base de Datos
public class Order {
    private Long id;
    private double totalAmount;

    public void calculateTax() { /*...*/ }
    
    // VIOLACIÓN: Lógica de impresión en la clase de datos
    public void printInvoiceHTML() {
        System.out.println("<html><body>Pedido: " + id + "</body></html>");
    }

    // VIOLACIÓN: Lógica de persistencia directamente acoplada
    public void saveToDatabase() {
        String sql = "INSERT INTO orders VALUES...";
        // Ejecución SQL con connection manager...
    }
}
// 1. Entidad del negocio pura (Una sola responsabilidad: Datos de Pedido)
public class Order {
    private Long id;
    private double totalAmount;
    // getters, setters, constructor, calculateTax()...
}

// 2. Clase de Presentación (Responsabilidad: Formatear facturas)
public class InvoicePrinter {
    public String formatToHTML(Order order) {
        return "<html><body>Pedido: " + order.getId() + "</body></html>";
    }
}

// 3. Clase de Persistencia (Responsabilidad: Guardar datos en DB)
public class OrderRepository {
    public void save(Order order) {
        String sql = "INSERT INTO orders VALUES...";
        // Ejecución SQL
    }
}

O: Open/Closed Principle (Abierto / Cerrado)

El principio Abierto/Cerrado dicta que las entidades de software deben estar abiertas a la extensión, pero cerradas a la modificación. Debes poder añadir nuevas funcionalidades sin alterar el código existente que ya ha sido probado y compilado. 

// Si queremos añadir un nuevo método de pago (ej. PayPal),
// estamos obligados a MODIFICAR esta clase existente, rompiendo OCP.
public class PaymentProcessor {
    public void processPayment(String type, double amount) {
        if (type.equals("CREDIT_CARD")) {
            // Lógica de pasarela tarjeta de crédito
        } else if (type.equals("CASH")) {
            // Lógica pago en efectivo
        }
        // VIOLACIÓN: Cualquier nuevo tipo de pago añade más ramas else-if aquí
    }
}
// Definimos una abstracción abierta a extensiones
public interface PaymentMethod {
    void pay(double amount);
}

// Implementaciones concretas (cerradas a modificaciones externas)
public class CreditCardPayment implements PaymentMethod {
    public void pay(double amount) { /* Lógica tarjeta */ }
}

public class CashPayment implements PaymentMethod {
    public void pay(double amount) { /* Lógica efectivo */ }
}

// Si queremos añadir PayPal, simplemente creamos una nueva clase
public class PaypalPayment implements PaymentMethod {
    public void pay(double amount) { /* Lógica PayPal */ }
}

// El procesador no se modifica nunca más, se mantiene CERRADO.
public class PaymentProcessor {
    public void processPayment(PaymentMethod method, double amount) {
        method.pay(amount);
    }
}

L: Liskov Substitution Principle (Sustitución de Liskov)

Este principio, propuesto por Barbara Liskov, establece que los objetos de una subclase deben poder reemplazar a los objetos de la superclase sin alterar el comportamiento correcto del programa. La herencia debe reflejar una relación semántica estricta. 

public class Rectangulo {
    protected int ancho, alto;
    public void setAncho(int a) { this.ancho = a; }
    public void setAlto(int h) { this.alto = h; }
    public int getArea() { return ancho * alto; }
}

// VIOLACIÓN: Un cuadrado no es intercambiable matemáticamente con un rectángulo
// porque modificar el ancho modifica también el alto, rompiendo supuestos.
public class Cuadrado extends Rectangulo {
    @Override
    public void setAncho(int a) {
        this.ancho = a;
        this.alto = a; // Daño colateral
    }
    @Override
    public void setAlto(int h) {
        this.ancho = h;
        this.alto = h; // Daño colateral
    }
}
// Definimos una interfaz común basada en el comportamiento deseado
public interface FiguraGeometrica {
    int getArea();
}

// Cada figura se responsabiliza de sus dimensiones específicas
public class Rectangulo implements FiguraGeometrica {
    private int ancho, alto;
    public Rectangulo(int ancho, int alto) {
        this.ancho = ancho;
        this.alto = alto;
    }
    public int getArea() { return ancho * alto; }
}

public class Cuadrado implements FiguraGeometrica {
    private int lado;
    public Cuadrado(int lado) {
        this.lado = lado;
    }
    public int getArea() { return lado * lado; }
}

I: Interface Segregation Principle (Segregación de Interfaces)

El principio de Segregación de Interfaces dice que los clientes no deben estar obligados a depender de interfaces que no utilizan. Es preferible tener muchas interfaces pequeñas y cohesivas en lugar de una única interfaz "gorda" y multiuso. 

// Interfaz sobredimensionada
public interface Trabajador {
    void trabajar();
    void comer(); // Interfaz gorda
}

// VIOLACIÓN: Un robot trabajador no come, pero está obligado a
// implementar el método comer() y lanzar una excepción inútil.
public class Robot implements Trabajador {
    public void trabajar() { /* Escribe código */ }
    
    public void comer() {
        throw new UnsupportedOperationException("Los robots no comen");
    }
}
// Segregamos la interfaz en componentes de rol específicos
public interface Trabajable {
    void trabajar();
}

public interface Comible {
    void comer();
}

// El humano implementa ambos roles
public class Humano implements Trabajable, Comible {
    public void trabajar() { /* Programar */ }
    public void comer() { /* Almorzar */ }
}

// El robot solo depende de lo que realmente requiere
public class Robot implements Trabajable {
    public void trabajar() { /* Ensamblar autos */ }
}

D: Dependency Inversion Principle (Inversión de Dependencias)

El principio de Inversión de Dependencias dicta que: 1. Los módulos de alto nivel no deben depender de módulos de bajo nivel; ambos deben depender de abstracciones. 2. Las abstracciones no deben depender de los detalles; los detalles deben depender de las abstracciones. 

// Módulo de bajo nivel (Detalle técnico de base de datos)
public class MySQLDatabase {
    public void saveRecord(String data) { /* INSERT SQL */ }
}

// Módulo de alto nivel (Lógica de Negocio)
// VIOLACIÓN: UserService está acoplado de forma rígida a MySQLDatabase.
// Si queremos cambiar a MongoDB o simular para pruebas, tenemos que modificar la clase.
public class UserService {
    private final MySQLDatabase database;

    public UserService() {
        this.database = new MySQLDatabase(); // Acoplamiento duro
    }

    public void registerUser(String name) {
        database.saveRecord(name);
    }
}
// Abstracción (Interfaz compartida)
public interface DatabaseConnection {
    void saveRecord(String data);
}

// Bajo nivel implementa la abstracción
public class MySQLDatabase implements DatabaseConnection {
    public void saveRecord(String data) { /* INSERT SQL */ }
}

public class MongoDatabase implements DatabaseConnection {
    public void saveRecord(String data) { /* NoSQL save */ }
}

// Alto nivel depende UNICAMENTE de la abstracción y se le inyecta por constructor.
public class UserService {
    private final DatabaseConnection database;

    // Inyección de dependencias
    public UserService(DatabaseConnection database) {
        this.database = database;
    }

    public void registerUser(String name) {
        database.saveRecord(name);
    }
}
