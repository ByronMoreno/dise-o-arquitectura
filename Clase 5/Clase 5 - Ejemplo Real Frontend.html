Frontend SGA: Estructuras y Justificación

Explora las arquitecturas de software modernas para la capa del cliente (Frontend) aplicadas al Sistema de Gestión Académica (SGA). Analiza las estructuras físicas de carpetas y archivos para **SPA Monolítica, Micro-frontends, Clean Architecture en Frontend y Server-Side Rendering (Next.js)**.

1. SPA Monolítica (Single Page Application)

En un monolito frontend, todas las interfaces (Matriculación, Notas, Cobros, Calendario) y sus estados lógicos conviven en un solo repositorio y se compilan en un único lote estático de archivos JavaScript y CSS (`bundle.js`).

Árbol de Directorios (React Monolith SPA)

  • 📂 sga-frontend-monolith // Un solo repositorio
    • 📄 package.json // Un set de dependencias global
    • 📂 src
      • 📄 main.tsx // Punto de arranque React
      • 📄 App.tsx // Router central con todas las rutas
      • 📂 components // Componentes comunes UI (Botones, Inputs)
      • 📂 pages // Módulos organizados conceptualmente
        • 📂 matricula
          • 📄 InscripcionCursos.tsx
          • 📄 HorarioVisualizador.tsx
        • 📂 notas
          • 📄 BoletaNotas.tsx
        • 📂 pagos
          • 📄 HistorialPagos.tsx
      • 📂 store // Estado global único compartido (Redux / Zustand)

Justificación de SPA Monolítica:

  • Adecuación: Equipos de desarrollo pequeños, o fases iniciales del portal de estudiantes donde la interfaz es sencilla.
  • Ventajas: Simplicidad extrema en compilación y despliegue (un solo comando de build genera archivos estáticos fáciles de subir a servicios como Netlify o AWS S3). Compartir componentes UI y el estado de la sesión del alumno (tokens, perfil) es trivial.
  • Desventajas: El tamaño del archivo final compilado (`bundle.js`) se infla con el tiempo, ralentizando el primer inicio en móviles de estudiantes con conexiones lentas. Además, un error crítico de compilación en el módulo de pagos puede inhabilitar todo el portal de calificaciones.

2. Micro-frontends

Descompone el frontend en pequeñas aplicaciones independientes desplegables y compilables de forma autónoma. Un contenedor (*Shell*) actúa como anfitrión para renderizar y cargar dinámicamente en el navegador cada módulo (Matrícula, Notas) utilizando tecnologías como **Module Federation (Webpack/Vite)** o **Single-spa**.

Árbol de Directorios (Module Federation)

  • 📂 sga-microfrontends // Estructura Monorepo o Multi-repo
    • 📂 shell-app // Módulo contenedor / Orquestador
      • 📄 webpack.config.js // Configura Module Federation para consumir remotos
      • 📂 src
        • 📄 Header.tsx // Barra superior unificada
        • 📄 App.tsx // Carga rutas mediante importaciones dinámicas lazy
    • 📂 matricula-mfe // Micro-app 1 (Inscripciones)
      • 📄 package.json
      • 📄 webpack.config.js // Expone el módulo 'MatriculaWidget' al Shell
      • 📂 src
    • 📂 notas-mfe // Micro-app 2 (Boletas de Notas)
      • 📄 package.json
      • 📄 webpack.config.js // Expone el módulo 'NotasWidget' al Shell
      • 📂 src

Justificación de Micro-frontends:

  • Adecuación: Portales universitarios masivos operados por múltiples equipos de desarrollo independientes (ej. equipo de finanzas enfocado en pagos, equipo de secretaría enfocado en admisiones).
  • Ventajas: Independencia absoluta de despliegue. El equipo de admisiones puede subir cambios de matriculación a producción un viernes a las 11:00 PM sin riesgo de afectar el módulo de calificaciones de los profesores. Permite usar diferentes tecnologías (ej. admisiones en React y notas en Vue).
  • Desventajas: Complejidad de desarrollo local alta. Compartir estado global (como la sesión del usuario) requiere definir contratos estrictos. Riesgo de sobrecarga de carga inicial si no se configuran librerías compartidas (ej. descargar React varias veces en cada módulo).

3. Arquitectura en Capas / Clean Architecture en Frontend

Aplica los principios de desacoplamiento de *Clean Architecture* en el cliente. La lógica del negocio (reglas, validación de créditos, cálculo de promedios) y las APIs se independizan por completo del Framework UI (React/Vue/Angular), permitiendo cambiar de librería visual sin rescribir el núcleo del sistema.

Árbol de Carpetas (Clean Architecture Frontend)

  • 📂 sga-frontend-clean
    • 📂 src
      • 📂 data // CAPA 1: Infraestructura (HTTP, LocalStorage)
        • 📄 MatriculaRepositoryImpl.ts // Realiza el fetch HTTP a la API
        • 📄 StorageServiceImpl.ts
      • 📂 domain // CAPA 2: Lógica pura del negocio (Casos de Uso e interfaces)
        • 📄 MatriculaRepository.ts // Interfaz / Contrato
        • 📄 InscribirAlumnoUseCase.ts // Regla pura: Valida créditos máximos
        • 📄 StudentEntity.ts
      • 📂 presentation // CAPA 3: Visual / UI (Acoplado a React/Vue)
        • 📂 views // Vistas o Páginas
          • 📄 MatriculaScreen.tsx
        • 📂 components // Botones, Tablas
        • 📂 hooks // Controladores locales que ligan Domain con View
          • 📄 useMatricula.ts

Justificación de Capas / Clean Frontend:

  • Adecuación: Portales de software críticos de larga vida útil donde se prevé migrar o actualizar de tecnologías (ej. cambiar de React a Next.js o Svelte) sin perder años de lógica e interfaces de comunicación ya programadas.
  • Ventajas: Desacoplamiento absoluto. Las pruebas unitarias son muy rápidas de ejecutar ya que no requieren levantar componentes visuales ni mocks del DOM para testear reglas lógicas de cálculo de promedios de notas.
  • Desventajas: Incrementa la sobrecarga de código de inicio. Requiere escribir múltiples interfaces y adaptadores para mapear objetos de datos simples, lo que puede ralentizar el desarrollo inicial de vistas sencillas.

4. Server-Side Rendering (SSR) e Isomórfica

Las aplicaciones isomórficas comparten la ejecución del código en el servidor y en el cliente. Al cargar una página, el Servidor pre-renderiza el HTML completo con los datos académicos correspondientes e inmediatamente lo envía listo para visualizar al navegador (hidratación del cliente).

Árbol de Directorios (Next.js App Router)

  • 📂 sga-nextjs-app
    • 📄 package.json
    • 📂 app // Enrutamiento basado en archivos
      • 📄 layout.tsx // Plantilla de layout global
      • 📄 page.tsx // Landing principal del portal de la U
      • 📂 matricula // Ruta: /matricula
        • 📄 page.tsx // Componente de Servidor: consulta la API en el backend directamente
      • 📂 notas // Ruta: /notas
        • 📄 page.tsx
      • 📂 api // Rutas de Backend ligeras integradas en Next.js
        • 📂 auth
          • 📄 route.ts

Justificación de SSR / Next.js:

  • Adecuación: Portales universitarios públicos con requerimientos altos de SEO (para que buscadores indexen el catálogo de cursos) y necesidad de tiempos de carga inicial ultrarrápidos.
  • Ventajas: Velocidad de despliegue inicial asombrosa. El servidor pre-carga los datos de notas directamente de la base de datos interna y los envía como HTML renderizado, ahorrando latencias de fetch en el navegador. La seguridad mejora al no exponer URLs del backend al cliente web.
  • Desventajas: Requiere servidores activos corriendo node.js (mayor costo computacional que hospedar estáticos ordinarios). La depuración de código se vuelve compleja al tener código que se ejecuta en el servidor y código que se ejecuta en el navegador (ej. `window is not defined`).
