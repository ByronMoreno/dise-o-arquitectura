Sistema de Gestión Académica (SGA): 5 Estructuras

Aprende cómo estructurar las carpetas y archivos de un Sistema de Gestión Académica (SGA) —que incluye Matriculación, Calificaciones, Horarios e Impuestos/Pagos— modelado bajo los cinco estilos arquitectónicos principales estudiados en clase.

1. Arquitectura Monolítica

En un monolito académico, todos los módulos de negocio (Matriculación, Calificaciones, Pagos) coexisten dentro del mismo espacio de nombres y se compilan en un único paquete físico. Comparten la misma memoria de ejecución de la JVM y una base de datos relacional centralizada.

Árbol de Directorios del Monolito Académico

  • 📂 academic-monolith // Proyecto único Maven
    • 📄 pom.xml // Dependencias globales del sistema
    • 📂 src/main/java/com/unibe/academic
      • 📄 AcademicMonolithApplication.java // Entrada única
      • 📂 matriculas // Módulo de Matriculación
        • 📄 MatriculaController.java
        • 📄 MatriculaService.java
        • 📄 Matricula.java
      • 📂 calificaciones // Módulo de Calificaciones
        • 📄 NotaController.java
        • 📄 NotaService.java
        • 📄 Nota.java
      • 📂 pagos // Módulo de Pagos y Pensiones
        • 📄 PagoController.java
        • 📄 PagoService.java
        • 📄 Factura.java

Justificación Técnica del Monolito:

  • Adecuación: Ideal para universidades pequeñas en fases iniciales de desarrollo o institutos con flujos de carga controlados.
  • Ventajas: Transaccionalidad inmediata y consistente (ACID). Un pago y una matrícula se procesan en la misma transacción SQL sin riesgo de desincronización física. Pruebas y despliegues muy simples.
  • Desventajas: Punto único de fallo (SPOF). Si colapsa el módulo de matriculación durante el día de registro de asignaturas, se cae todo el servidor, impidiendo a los profesores subir notas o a los alumnos pagar sus pensiones.

2. Arquitectura en Capas (Layered)

En este enfoque, el sistema académico se organiza de manera horizontal por sus responsabilidades técnicas en lugar de dominios de negocio. Las dependencias fluyen estrictamente hacia abajo: la capa de Presentación consume la de Servicios, y esta consume la de Repositorios.

Árbol de Directorios de la Arquitectura en Capas

  • 📂 academic-layered
    • 📄 pom.xml
    • 📂 src/main/java/com/unibe/academic/layered
      • 📄 AcademicLayeredApplication.java
      • 📂 controller // CAPA 1: Presentación / Controladores API
        • 📄 MatriculaController.java
        • 📄 NotaController.java
        • 📄 PagoController.java
      • 📂 service // CAPA 2: Lógica de Negocio y Reglas Académicas
        • 📄 MatriculaService.java
        • 📄 NotaService.java
        • 📄 PagoService.java
      • 📂 repository // CAPA 3: Infraestructura y Acceso a Base de Datos (JPA)
        • 📄 MatriculaRepository.java
        • 📄 NotaRepository.java
        • 📄 PagoRepository.java
      • 📂 model // Capa transversal de Entidades del Dominio
        • 📄 Matricula.java
        • 📄 Nota.java
        • 📄 Factura.java

Justificación Técnica del Diseño en Capas:

  • Adecuación: Recomendable para sistemas medianos que valoran el desacoplamiento técnico y la facilidad de mantenimiento a largo plazo.
  • Ventajas: Separación de Incumbencias (SoC). Si la universidad decide migrar su base de datos física de PostgreSQL a Oracle DB, solo se ve afectada la capa de `repository`, manteniendo intactas las capas de negocio y de controladores.
  • Desventajas: Sobrecarga de código y latencia. Operaciones de lectura simples (como consultar la nota de un alumno) deben cruzar obligatoriamente todas las capas secuencialmente sin aportar valor lógico real (efecto sándwich).

3. Estilo Cliente-Servidor

Separa la ejecución física del sistema. El Servidor expone un API REST y valida las reglas comerciales, mientras que el Cliente corre localmente en el computador o dispositivo móvil del estudiante/profesor, solicitando datos remotos mediante HTTP.

Árbol de Carpetas del Sistema Cliente-Servidor

  • 📂 academic-client-server
    • 📂 academic-backend-server // PROYECTO 1: Backend API
      • 📄 pom.xml
      • 📂 src/main/java/com/unibe/academic/server
        • 📄 AcademicServerApplication.java
        • 📄 MatriculaApiController.java // Retorna JSON
        • 📄 NotaApiController.java
    • 📂 academic-desktop-client // PROYECTO 2: UI en Swing o JavaFX
      • 📄 pom.xml
      • 📂 src/main/java/com/unibe/academic/client
        • 📄 AcademicClientApplication.java
        • 📄 PortalEstudianteFrame.java // Interfaz Gráfica
        • 📄 AcademicHttpClient.java // Consume REST del servidor

Justificación Técnica de Cliente-Servidor:

  • Adecuación: Entornos donde se requiere ofrecer múltiples canales de acceso (como un portal Web de alumnos, una aplicación móvil Android/iOS de profesores y terminales pesadas para secretaría).
  • Ventajas: Centralización de reglas críticas y seguridad en el Servidor. Los clientes son independientes y no tienen contacto directo con la base de datos, lo que incrementa la seguridad de la red.
  • Desventajas: El Servidor centralizado representa un cuello de botella y un Punto Único de Fallo. Si el servidor se apaga, ninguna aplicación cliente puede iniciar sesión o realizar consultas locales.

4. SOA (Service-Oriented Architecture)

SOA es el estilo de integración empresarial por excelencia. Conecta el software académico con sistemas externos y sistemas legados heredados (ej. sistema financiero COBOL, sistema de control de accesos por torniquetes, etc.) utilizando un **Bus de Servicios Empresariales (ESB)** que transforma formatos mediante contratos de red rígidos (SOAP / XML / WSDL).

Árbol de Directorios del Entorno SOA

  • 📂 academic-soa-enterprise
    • 📂 academic-esb-router // Módulo de integración ESB (ej. Apache Camel o Mule)
      • 📄 esb-config.xml // Enrutamiento y transformación XSLT (XML a JSON)
    • 📂 soap-matriculas-service // Servicio SOAP de Matrículas
      • 📄 pom.xml
      • 📂 src/main/resources/wsdl
        • 📄 matriculas.wsdl // Contrato estricto XML
    • 📂 legacy-finance-adapter // Conector al sistema contable heredado de la universidad
      • 📄 COBOLConnector.java

Justificación Técnica de SOA:

  • Adecuación: Universidades tradicionales de gran tamaño que ya cuentan con sistemas financieros legados, servicios de directorio activo corporativos y plataformas LMS externas, y necesitan integrarlos sin tener que rehacerlos.
  • Ventajas: Alta reusabilidad de sistemas legados de alto costo. Interoperabilidad multiplataforma garantizada gracias a los estándares corporativos rígidos WSDL/SOAP.
  • Desventajas: El ESB centralizado se vuelve un cuello de botella de rendimiento y organizacional (cualquier cambio requiere reconfigurar el bus). El formato XML/SOAP es sumamente pesado de procesar y complejo de desarrollar.

5. Arquitectura de Microservicios

Descompone el SGA en servicios autónomos desplegables independientemente. Cada microservicio administra su propio almacenamiento físico (Database per Service) y se comunican asíncronamente mediante colas de eventos (RabbitMQ / Kafka) o peticiones HTTP JSON / gRPC ligeras.

Árbol de Carpetas de Microservicios Académicos

  • 📂 academic-microservices
    • 📂 academic-api-gateway // Puerta de entrada perimetral (JWT Validation & Load Balancing)
      • 📄 application.yml
    • 📂 enrollment-service // Servicio de Matriculación
      • 📄 pom.xml
      • 📂 src/main/resources
        • 📄 application.yml // Conecta a Redis Cache para inscripción rápida
    • 📂 grades-service // Servicio de Calificaciones e Historial
      • 📄 pom.xml
      • 📂 src/main/resources
        • 📄 application.yml // Conecta a MongoDB (Catálogo de Cursos e historial)
    • 📂 billing-service // Servicio de Facturación y Cobro
      • 📄 pom.xml
      • 📂 src/main/resources
        • 📄 application.yml // Conecta a PostgreSQL (Transaccional ACID)

Justificación Técnica de Microservicios:

  • Adecuación: Recomendado para universidades masivas con decenas de miles de alumnos y alta demanda transaccional temporal en matriculación de asignaturas.
  • Ventajas: **Resiliencia extrema e independencia de escala**. El microservicio de `enrollment-service` puede escalarse a 20 instancias en Kubernetes durante la semana de matrículas utilizando una base de datos distribuida optimizada, mientras que el resto de los módulos operan de forma estable sin consumir memoria ni colapsar.
  • Desventajas: Alta complejidad de diseño. Dificultad para mantener transacciones atómicas de forma nativa entre bases de datos separadas (ej. anular una matrícula si falla el cobro bancario exige aplicar patrones de Saga distributiva). Requiere una infraestructura Cloud compleja y costosa.
